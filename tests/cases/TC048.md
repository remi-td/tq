# Test Case TC048: Table Formatting - Mixed Data Types Alignment

## Purpose

Verify that tables with mixed data types (strings, integers, decimals, dates, timestamps) display with correct type-specific alignment rules and that padding works correctly for each type.

## Scope

**Testing:**
- Left-alignment for text types (VARCHAR, CHAR)
- Right-alignment for numeric types (INTEGER, DECIMAL, FLOAT)
- Alignment for date/time types (DATE, TIME, TIMESTAMP)
- Mixed types in same table
- Column width calculation across different type widths

**Not Testing:**
- Type preservation in JSON (covered in TC016)
- NULL handling (covered in TC046)
- Very large tables

## Prerequisites

- tq REPL mode active
- Live Teradata database connection
- Ability to query tables with mixed types or construct test queries

## Test Procedure

### Setup

```bash
# Start tq in REPL mode
./target/release/tq
```

### Execution Steps

**Step 1: Query with all major data types**

```sql
tq> SELECT
    CAST('Name' AS VARCHAR(20)) AS text_col,
    CAST(12345 AS INTEGER) AS int_col,
    CAST(123.45 AS DECIMAL(10,2)) AS decimal_col,
    CAST(DATE '2026-01-18' AS DATE) AS date_col,
    CAST(TIMESTAMP '2026-01-18 10:30:45' AS TIMESTAMP(0)) AS timestamp_col;
```

**Expected outcome:**
- text_col is left-aligned
- int_col is right-aligned
- decimal_col is right-aligned with decimal point aligned
- date_col formatting is consistent
- timestamp_col formatting is consistent
- All columns maintain proper spacing and alignment

**Step 2: Verify alignment with varying widths**

```sql
tq> SELECT
    'A' AS t1,
    'Longer' AS t2,
    'Very Long String' AS t3,
    1 AS n1,
    12345 AS n2,
    9999999 AS n3,
    0.1 AS d1,
    123.456 AS d2;
```

**Expected outcome:**
- Short text "A" is left-aligned in its column
- Long text "Very Long String" is left-aligned in wider column
- Small number 1 is right-aligned
- Large number 9999999 is right-aligned
- Decimals are right-aligned with consistent decimal handling
- Column widths adjust to content, not fixed across types

**Step 3: Test realistic mixed-type query**

```sql
tq> SELECT TOP 5
    TableName,              -- VARCHAR
    TableKind,              -- CHAR(1)
    CreatorName,            -- VARCHAR
    CreateTimeStamp,        -- TIMESTAMP
    LastAlterTimeStamp,     -- TIMESTAMP
    RequestText             -- VARCHAR (can be NULL)
    FROM DBC.TablesV
    WHERE DatabaseName = DATABASE
    ORDER BY TableName;
```

**Expected outcome:**
- VARCHAR columns (TableName, CreatorName) are left-aligned
- CHAR column (TableKind) is left-aligned
- TIMESTAMP columns are formatted consistently
- RequestText (can be NULL or long) aligns properly
- All alignment rules are applied correctly

**Step 4: Test numeric precision alignment**

```sql
tq> SELECT
    1 AS small_int,
    1000000 AS large_int,
    0.1 AS small_dec,
    12345.6789 AS large_dec,
    0.00001 AS tiny_dec;
```

**Expected outcome:**
- All numeric values are right-aligned
- Decimal points may or may not align (depends on implementation)
- Column widths accommodate the largest value in each column
- Small values don't cause excessive padding

### Verification

**Alignment Rules:**

1. **Text Types (VARCHAR, CHAR):**
   - [ ] All text values are left-aligned within their column
   - [ ] Example: `│ Name     ┆` not `│     Name ┆`

2. **Integer Types (INTEGER, BIGINT, SMALLINT):**
   - [ ] All integer values are right-aligned
   - [ ] Example: `┆    12345 │` not `┆ 12345    │`

3. **Decimal Types (DECIMAL, NUMERIC, FLOAT):**
   - [ ] All decimal values are right-aligned
   - [ ] Example: `┆  123.45 │` not `┆ 123.45  │`
   - [ ] Decimal points may optionally align vertically

4. **Date Types:**
   - [ ] Dates are formatted consistently
   - [ ] Alignment is appropriate (typically left or center)
   - [ ] Format is readable (e.g., "2026-01-18")

5. **Timestamp Types:**
   - [ ] Timestamps are formatted consistently
   - [ ] Format includes both date and time
   - [ ] Example: "2026-01-18 10:30:45"

**Column Width Verification:**

For each column:
- [ ] Width accommodates the widest value
- [ ] Width is not excessively large (no excessive padding)
- [ ] Different types have different widths (not uniform)

**Visual Inspection:**

Draw imaginary vertical lines through the table:
- [ ] Text starts at column left edge
- [ ] Numbers end at column right edge (before separator)
- [ ] Separators (┆) are perfectly vertical
- [ ] Headers align with their data type's alignment rule

## Expected Results

**Correct Mixed-Type Alignment Example:**

```
╭─────────────┬─────────┬──────────────┬────────────┬─────────────────────╮
│ text_col    ┆ int_col ┆ decimal_col  ┆ date_col   ┆ timestamp_col       │
╞═════════════╪═════════╪══════════════╪════════════╪═════════════════════╡
│ Name        ┆   12345 ┆       123.45 ┆ 2026-01-18 ┆ 2026-01-18 10:30:45 │
╰─────────────┴─────────┴──────────────┴────────────┴─────────────────────╯
```

**Key Characteristics:**
- "Name" (text): left-aligned with space after
- "12345" (int): right-aligned with space before
- "123.45" (decimal): right-aligned
- "2026-01-18" (date): formatted consistently
- "2026-01-18 10:30:45" (timestamp): full format

**Alignment Pattern Illustration:**

```
Text:      │ Value     ┆  (left-aligned, space after)
Integer:   ┆     12345 │  (right-aligned, space before)
Decimal:   ┆    123.45 │  (right-aligned, space before)
```

**Anti-Pattern (Should NOT Occur):**

```
╭─────────────┬─────────┬──────────────┬────────────┬─────────────────────╮
│ text_col    ┆ int_col ┆ decimal_col  ┆ date_col   ┆ timestamp_col       │
╞═════════════╪═════════╪══════════════╪════════════╪═════════════════════╡
│      Name   ┆ 12345   ┆ 123.45       ┆ 2026-01-18 ┆ 2026-01-18 10:30:45 │
╰─────────────┴─────────┴──────────────┴────────────┴─────────────────────╯
```

This shows:
- "Name" right-aligned (wrong for text)
- "12345" left-aligned (wrong for integer)
- "123.45" left-aligned (wrong for decimal)

## Pass/Fail Criteria

**PASS:**
- Text columns are left-aligned
- Numeric columns (integer and decimal) are right-aligned
- Date/timestamp columns are formatted consistently
- Column widths are appropriate for each type
- Alignment is maintained across all rows
- Headers align according to their column's data type

**FAIL:**
- Text columns are right-aligned
- Numeric columns are left-aligned
- Inconsistent date/timestamp formatting
- All columns have same alignment (ignoring type)
- Column widths are uniform (not type-appropriate)
- Headers misalign with data

## Notes

**Alignment Rationale:**

Standard table formatting conventions:
1. **Text left-aligned:** Easier to scan vertically, natural reading direction
2. **Numbers right-aligned:** Aligns decimal points, easier to compare magnitudes
3. **Dates/times:** Usually left or center, must be consistent

**Teradata Type Mapping:**

Common Teradata types and their alignment:
- VARCHAR, CHAR, CLOB → left
- INTEGER, BIGINT, SMALLINT, BYTEINT → right
- DECIMAL, NUMERIC, FLOAT, REAL → right
- DATE, TIME, TIMESTAMP → left or center (consistent)
- INTERVAL → left or right (depends on representation)

**comfy-table Configuration:**

The fix should use comfy-table's cell alignment features:
```rust
use comfy_table::CellAlignment;

cell.set_alignment(CellAlignment::Left);   // for text
cell.set_alignment(CellAlignment::Right);  // for numbers
```

**Column Width Consideration:**

Different types may have different natural widths:
- CHAR(1): narrow (1-3 chars wide)
- VARCHAR: variable (adjust to content)
- INTEGER: moderate (10-12 chars for max values)
- DECIMAL(10,2): moderate (12-14 chars)
- DATE: fixed (10 chars: "YYYY-MM-DD")
- TIMESTAMP: wider (19+ chars: "YYYY-MM-DD HH:MM:SS")

Column widths should reflect these natural sizes, not be uniform.
