## Purpose

Verify that tq can handle large result sets efficiently with streaming and client-side limits.

## Scope

This test validates:
- Large result set handling
- Memory efficiency (streaming)
- Client-side row limit (--limit)
- Performance with different formats
- No memory exhaustion

## Prerequisites

- tq binary is built and available
- `.env` file configured with valid Teradata connection credentials
- Access to large table or ability to generate large result set

## Test Procedure

### Step 1: Query returning many rows (no limit)
```bash
# Using credentials from .env file
# Create large result (adjust for test environment)
tq query "SELECT * FROM large_table SAMPLE 1000" --format csv > /tmp/large_result.csv
wc -l /tmp/large_result.csv
rm /tmp/large_result.csv
```

### Step 2: Use client-side limit
```bash
tq query --limit 10 "SELECT * FROM large_table"
```

### Step 3: Large result with JSON
```bash
tq query --limit 100 --format json "SELECT * FROM large_table" | jq 'length'
```

### Step 4: Large result with CSV
```bash
tq query --limit 100 --format csv "SELECT * FROM large_table" | wc -l
```

### Step 5: Monitor memory usage (if possible)
```bash
# Run in background and monitor
tq query "SELECT * FROM large_table SAMPLE 10000" --format csv > /tmp/output.csv &
PID=$!
# Monitor memory
while kill -0 $PID 2>/dev/null; do
  ps -o rss= -p $PID | awk '{print $1/1024 " MB"}'
  sleep 1
done
rm /tmp/output.csv
```

### Step 6: Large result to file
```bash
tq query --output /tmp/large.csv --format csv "SELECT * FROM large_table SAMPLE 5000"
ls -lh /tmp/large.csv
rm /tmp/large.csv
```

### Step 7: Verify streaming (time to first byte)
```bash
time (tq query "SELECT * FROM large_table SAMPLE 10000" --format csv | head -10 > /dev/null)
# Should be fast even for large result set
```

## Pass/Fail Criteria

**PASS if:**
- Can handle thousands of rows without errors
- Memory usage remains reasonable (streaming)
- --limit correctly restricts rows
- Large results work in all formats
- Time to first output is fast (streaming)
- No crashes or memory exhaustion

**FAIL if:**
- Memory grows unbounded with result size
- Crashes on large result sets
- --limit doesn't work
- Performance degrades significantly
- Out of memory errors

## Notes

- Streaming is critical for large results
- Should not buffer entire result set in memory
- --limit is client-side (still fetches from DB)
- For server-side limiting, use TOP/SAMPLE in SQL
- Consider testing with 10K, 100K, 1M rows if possible
- Memory monitoring may be system-specific
- Good test for performance regression
