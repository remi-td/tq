# TC-042-001: Semicolons Inside Quoted Strings (Bug #28)

**Test ID:** TC-042-001
**Feature:** SQL Parser - Quote-Aware Semicolon Splitting
**Priority:** P0 - Critical
**Test Type:** Unit
**Sprint:** 42
**Created:** 2026-03-21
**Requirement References:** REQ-PARSE-001, REQ-PARSE-005, REQ-PARSE-006, REQ-PARSE-007, AC-1, AC-2, AC-11
**GitHub Issue:** #28 - Semicolons inside quoted strings split statements incorrectly

---

## Objective

Verify that the new state-machine parser does NOT split SQL statements at semicolons that appear inside single-quoted string literals, correctly handles the `''` escape sequence within strings, and reports errors for unterminated strings.

## Background

Bug #28 describes a failure mode where:
```sql
INSERT INTO messages VALUES ('Hello; World');
```
was parsed as TWO statements by the naive `split(';')` approach:
- Statement 1: `INSERT INTO messages VALUES ('Hello`
- Statement 2: ` World')`

Both fragments are invalid SQL. The new parser must track quoted-string context and treat any semicolon inside `'...'` as part of the string content.

---

## Test Cases

All tests are unit tests in `src/sql/parser.rs` `#[cfg(test)]` module.

### TS42-U01: Semicolon inside single-quoted string

```rust
#[test]
fn test_semicolon_in_single_quoted_string() {
    // Bug #28: semicolon inside string must not split the statement
    let sql = "INSERT INTO messages VALUES ('Hello; World');";
    let statements = parse_statements(sql).expect("parse should succeed");
    assert_eq!(statements.len(), 1, "should be exactly 1 statement");
    assert_eq!(statements[0].statement_number, 1);
    assert_eq!(statements[0].start_line, 1);
    // The SQL content must contain the full string including the semicolon
    assert!(
        statements[0].sql.contains("'Hello; World'"),
        "string content with semicolon must be preserved"
    );
}
```

**Expected Result:** 1 statement returned; the string `'Hello; World'` is intact.

### TS42-U05: Realistic INSERT with semicolon in value - two statements

```rust
#[test]
fn test_insert_with_semicolon_in_value_two_statements() {
    // Realistic multi-statement file where only the terminator semicolons split
    let sql = "INSERT INTO t VALUES ('a;b');\nSELECT * FROM t;";
    let statements = parse_statements(sql).expect("parse should succeed");
    assert_eq!(statements.len(), 2);
    // First statement has the string with semicolon inside
    assert!(statements[0].sql.contains("'a;b'"));
    // Second statement is a clean SELECT
    assert!(statements[1].sql.contains("SELECT"));
    assert_eq!(statements[0].start_line, 1);
    assert_eq!(statements[1].start_line, 2);
}
```

**Expected Result:** 2 statements; line numbers are accurate.

### TS42-U06: Single-quoted string with comment marker inside - not treated as comment

```rust
#[test]
fn test_comment_marker_inside_string_is_not_comment() {
    // REQ-PARSE-005: Inside a string, -- and /* are not special
    let sql = "SELECT '-- not a comment' AS s;";
    let statements = parse_statements(sql).expect("parse should succeed");
    assert_eq!(statements.len(), 1);
    assert!(statements[0].sql.contains("'-- not a comment'"));

    let sql2 = "SELECT '/* also not a comment */' AS s;";
    let statements2 = parse_statements(sql2).expect("parse should succeed");
    assert_eq!(statements2.len(), 1);
    assert!(statements2[0].sql.contains("'/* also not a comment */'"));
}
```

**Expected Result:** 1 statement per input; comment markers inside strings are passed through verbatim.

### TS42-U08: Unterminated string literal produces error

```rust
#[test]
fn test_unterminated_string_error() {
    // REQ-PARSE-007: EOF inside a string is a parse error
    // The error must identify the line number where the string opened
    let sql = "SELECT 'unterminated";
    let result = parse_statements(sql);
    assert!(
        result.is_err(),
        "unterminated string must produce an error, not silently truncate"
    );
    // Verify the error references line 1 (where the string started)
    let err = result.unwrap_err();
    // The error message or error type must identify line 1
    // Exact assertion form depends on ParseError type designed by architect:
    // assert_eq!(err.line, 1);
    // assert!(err.to_string().contains("line 1"));
    let err_str = format!("{err}");
    assert!(
        err_str.contains("1") || err_str.to_lowercase().contains("unterminated"),
        "error must mention line number or describe unterminated string: {err_str}"
    );
}
```

**Expected Result:** `Err(...)` variant returned; error references line 1.

---

### TS42-U09: Unterminated string on line 5 reports line 5

```rust
#[test]
fn test_unterminated_string_error_correct_line_number() {
    // REQ-PARSE-017: parse error must reference where the construct BEGAN, not EOF
    let sql = "SELECT 1;\nSELECT 2;\nSELECT 3;\nSELECT 4;\nSELECT 'unterminated";
    let result = parse_statements(sql);
    assert!(result.is_err());
    let err = result.unwrap_err();
    let err_str = format!("{err}");
    assert!(
        err_str.contains("5"),
        "error must reference line 5 where string started, got: {err_str}"
    );
}
```

**Expected Result:** `Err(...)` with line 5 in the error message.

## Acceptance Criteria

- [x] Semicolons inside `'...'` do NOT split statements (AC-1, REQ-PARSE-001)
- [x] `''` is treated as escaped quote, stays in-string (AC-2, REQ-PARSE-006)
- [x] Comment markers (`--`, `/*`) inside strings are passed through verbatim (REQ-PARSE-005)
- [x] Unterminated strings produce a parse error (REQ-PARSE-007)
- [x] Error for unterminated string references the correct line number (REQ-PARSE-017)

## Execution Notes

Run with: `cargo test --lib sql::parser::tests::test_semicolon`

All tests in this case are **no-database** unit tests. They can be executed in any environment with a Rust toolchain.

Note: Tests TS42-U08 and TS42-U09 require the `parse_statements()` function to return `Result<Vec<ParsedStatement>, ParseError>`. If the architect uses a different API for error reporting (e.g., returning an empty vec with a side-channel error), the assertion patterns must be updated to match the actual API.
