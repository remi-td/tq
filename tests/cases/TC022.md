## Purpose

Verify that tq never exposes passwords in output, logs, error messages, or process listings.

## Scope

This test validates:
- No passwords in stdout/stderr
- No passwords in error messages
- No passwords in verbose/debug output
- Password redaction in logs
- Process listing security
- .env file security

## Prerequisites

- tq binary is built and available
- `.env` file configured (passwords stored in file, not in command line)
- Unix-like system with ps command

## Test Procedure

### Step 1: Check process listing with password in connection string
```bash
# Start tq in background
tq -l "testuser:secretpass@testhost:1025/testdb" ping &
PID=$!
ps -f -p $PID
wait $PID
```

### Step 2: Check verbose output for password leakage
```bash
tq -vvv -l "testuser:secretpass@testhost:1025/testdb" ping 2>&1 | grep -i "secretpass" || echo "No password found (PASS)"
```

### Step 3: Check error output for password leakage
```bash
tq -l "testuser:secretpass@invalid-host-12345:1025/testdb" ping 2>&1 | grep -i "secretpass" || echo "No password found (PASS)"
```

### Step 4: Check connection string in error messages
```bash
tq -l "invalid_format:secretpass" ping 2>&1 | grep "secretpass" || echo "Password redacted (PASS)"
```

### Step 5: Check with password file
```bash
echo "secretpass" > /tmp/testpass
chmod 0600 /tmp/testpass
tq -l "testuser@testhost:1025/testdb" --password-file /tmp/testpass ping &
PID=$!
ps -f -p $PID | grep "secretpass" || echo "Password not in process list (PASS)"
wait $PID
rm /tmp/testpass
```

### Step 6: Check .env file usage doesn't leak password
```bash
# Using .env file (recommended approach)
tq -vvv ping 2>&1 | grep -i "secretpass\|password.*=" || echo "No password found in verbose output (PASS)"
```

### Step 7: Check environment variable exposure (explicit export)
```bash
export TQ_LOGON="testuser:secretpass@testhost:1025/testdb"
tq ping &
PID=$!
cat /proc/$PID/environ 2>/dev/null | grep "TQ_LOGON" && echo "WARNING: env vars visible in /proc" || echo "OK"
wait $PID
unset TQ_LOGON
```

### Step 8: Check failed authentication message
```bash
tq -l "testuser:wrongpass@testhost:1025/testdb" ping 2>&1 | grep "wrongpass" || echo "Password not in error (PASS)"
```

## Pass/Fail Criteria

**PASS if:**
- Passwords never appear in process listings
- Passwords never appear in verbose output
- Passwords never appear in error messages
- Passwords are redacted in all log output
- Connection strings are sanitized (password replaced with ***)
- Password file contents never exposed

**FAIL if:**
- Password visible in ps output
- Password visible in any output/logs
- Password visible in error messages
- No password redaction
- Security leak in any scenario

## Notes

- CRITICAL: Passwords must NEVER be exposed
- Process arguments are visible to all users (ps, /proc)
- Avoid passwords in CLI args (use .env file or --password-file)
- .env file is recommended for development: secure file with 0600 permissions
- Environment variables better than CLI args but still visible in /proc
- Best practice hierarchy:
  1. .env file (development/testing)
  2. --password-file (production scripts)
  3. Explicit environment variables (scripting)
  4. NEVER in command line arguments
- Consider using secrecy crate for Secret<String>
- Redaction format: user:***@host or user@host (omit entirely)
- This is a security audit test
- Test with real password patterns to ensure coverage
- .env file should be in .gitignore (already done)
