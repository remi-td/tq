# TC-044-003: build.rs Does Not Hardcode Absolute Build Path

**Sprint:** 44
**Feature:** Runtime Driver Library Resolution (Issue #31)
**Acceptance Criteria:** AC-4
**Type:** Unit Test (Code Inspection)
**Requires DB:** No
**Requires Binary:** No

---

## Objective

Verify that `build.rs` no longer emits `cargo:rustc-env=TERADATA_LIB_DIR` with an absolute CI build-time path. This is the root cause of Issue #31 (all released binaries fail because they have a CI runner path baked in).

## Preconditions

- `build.rs` exists in the project root
- The file is readable

## Test Scenarios

### Scenario 1: build.rs does not set TERADATA_LIB_DIR to an absolute path

**Setup:** Read `build.rs` as a string

**Action:** Search for the pattern `cargo:rustc-env=TERADATA_LIB_DIR` followed by an absolute path (starting with `/`)

**Expected:** No such pattern found. Either:
- The `cargo:rustc-env=TERADATA_LIB_DIR` line is completely absent, OR
- If it exists, it sets a relative path or a sentinel value (e.g., `.` or empty string)

**Assert:**
```rust
let content = std::fs::read_to_string("build.rs").unwrap();
// Must not contain absolute path assignment to TERADATA_LIB_DIR
assert!(
    !content.contains("cargo:rustc-env=TERADATA_LIB_DIR=/"),
    "build.rs must not set TERADATA_LIB_DIR to an absolute path"
);
```

### Scenario 2: option_env!("TERADATA_LIB_DIR") in client.rs is not the primary resolution path

**Setup:** Read `src/db/client.rs` as a string

**Action:** Check that `option_env!("TERADATA_LIB_DIR")` is used as a fallback (last resort or not at all), not as the primary/sole driver path

**Expected:** Either `option_env!("TERADATA_LIB_DIR")` is absent, or it appears in a fallback context (within the resolution chain, after exe-relative path)

**Assert:** The line `option_env!("TERADATA_LIB_DIR").unwrap_or(".")` or similar fallback pattern; NOT `option_env!("TERADATA_LIB_DIR").unwrap_or(".")` as the sole source.

## Implementation Location

`src/db/client.rs` test module or `tests/build_sanity.rs` (new file)

## Test Code

```rust
// In tests/build_sanity.rs or src/db/client.rs tests module

#[test]
fn test_build_rs_does_not_hardcode_absolute_teradata_lib_dir() {
    let build_rs = std::fs::read_to_string("build.rs")
        .expect("build.rs must be readable from project root");

    // The critical check: no absolute path assignment for TERADATA_LIB_DIR
    assert!(
        !build_rs.contains("cargo:rustc-env=TERADATA_LIB_DIR=/"),
        "build.rs must not set TERADATA_LIB_DIR to an absolute path. \
         This is the root cause of Issue #31: CI build paths baked into released binaries. \
         Found problematic pattern in build.rs."
    );
}

#[test]
fn test_client_rs_does_not_use_build_path_as_sole_driver_dir() {
    let client_rs = std::fs::read_to_string("src/db/client.rs")
        .expect("src/db/client.rs must be readable");

    // If option_env! is used, it must be as a fallback, not the primary path
    // The exe-relative path must be preferred
    if client_rs.contains("option_env!(\"TERADATA_LIB_DIR\")") {
        // That's OK as long as exe-relative path logic also exists
        assert!(
            client_rs.contains("current_exe") || client_rs.contains("resolve_driver"),
            "If option_env!(TERADATA_LIB_DIR) is used, exe-relative path resolution must also be present"
        );
    }
}
```

## Notes

- These tests must be run from the project root directory so relative paths to `build.rs` and `src/` work correctly.
- The test path `"build.rs"` is relative to the working directory during test execution, which is the project root for `cargo test`.
- If `cargo test` is run from a subdirectory, add the `CARGO_MANIFEST_DIR` env var approach:
  ```rust
  let manifest_dir = env!("CARGO_MANIFEST_DIR");
  let build_rs = std::fs::read_to_string(format!("{}/build.rs", manifest_dir)).unwrap();
  ```

## Pass Criteria

- `build.rs` does not contain `cargo:rustc-env=TERADATA_LIB_DIR=/` (absolute path)
- If `option_env!("TERADATA_LIB_DIR")` is used in client.rs, exe-relative resolution also exists
