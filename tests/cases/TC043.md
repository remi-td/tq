## Purpose

Verify that column name completion meets performance requirements: < 300ms for metadata query, < 50ms for cached completions.

## Scope

This test validates:
- First column completion (metadata query) < 300ms
- Cached column completion < 50ms
- Performance consistent across multiple completions
- Different tables cached independently
- Wide tables (many columns) handled efficiently

## Prerequisites

- tq binary built in release mode
- Valid Teradata connection credentials configured in .env
- Test database with tables of varying width
- REPL mode functional

## Test Procedure

### Step 1: Start REPL
```bash
tq repl
```

### Step 2: Measure first column completion (cold cache)
```sql
tq> SELECT * FROM employees WHERE <TAB>
# Record time from Tab press to column display
```

**Expected:** < 300ms

### Step 3: Measure cached column completion
```sql
tq> SELECT * FROM employees ORDER BY <TAB>
# Same table, cached
# Record time
```

**Expected:** < 50ms

### Step 4: Measure second table (different cache entry)
```sql
tq> SELECT * FROM departments WHERE <TAB>
# Different table, not cached
# Record time
```

**Expected:** < 300ms (new table)

### Step 5: Verify second table now cached
```sql
tq> SELECT * FROM departments ORDER BY <TAB>
# Record time
```

**Expected:** < 50ms

### Step 6: Return to first table (should still be cached)
```sql
tq> SELECT * FROM employees WHERE <TAB>
# Record time
```

**Expected:** < 50ms (still cached)

### Step 7: Test wide table (many columns)
```sql
# Use table with 50+ columns if available
tq> SELECT * FROM wide_table WHERE <TAB>
```

**Expected:** < 300ms even with many columns

### Step 8: Test prefix filtering performance
```sql
tq> SELECT * FROM employees WHERE e<TAB>
tq> SELECT * FROM employees WHERE em<TAB>
tq> SELECT * FROM employees WHERE emp<TAB>
```

**Expected:** All < 50ms (filtering cached data)

## Pass/Fail Criteria

**PASS if:**
- First column load < 300ms (95th percentile)
- Cached completion < 50ms (95th percentile)
- Multiple tables cached independently
- Wide tables handled within limits
- Prefix filtering instant
- No performance degradation

**FAIL if:**
- First load > 300ms consistently
- Cached completion > 50ms
- Cache doesn't work per-table
- Wide tables cause timeout
- Prefix filtering slow

## Notes

- Column queries faster than table queries (single table scan)
- Per-table caching critical for performance
- Wide tables may have display challenges separate from query time
- Metadata query time depends on table complexity
- Type hint formatting shouldn't add significant overhead
- Document number of columns in test tables
