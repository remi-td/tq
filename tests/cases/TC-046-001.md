## Purpose

Verify that after the Bug #35 fix, `quote_identifier()` converts the input to uppercase before wrapping it in double quotes. This is the root cause of `/sample dbc.tables;` failing: Teradata stores object names in uppercase and quoted identifiers are case-sensitive, so quoting lowercase input without uppercasing it causes a "not found" error.

The fix must also preserve SQL injection protection: embedded double quotes must still be doubled after uppercasing.

## Acceptance Criteria Coverage

- **AC-7**: Unit tests for `quote_identifier()` uppercase behavior
- **AC-5**: Case-insensitive table names work (quoting side — verified that the quoted form is uppercase)

## Prerequisites

- `src/sql/identifiers.rs` has `quote_identifier()` changed to uppercase identifiers before quoting
- `cargo test --lib` compiles successfully

## Test Procedure

### Test Implementation (in `src/sql/identifiers.rs` `#[cfg(test)]` module)

Add the following test functions to the existing `tests` module:

```rust
// TC-046-001-A: lowercase input uppercased
#[test]
fn test_quote_identifier_lowercase_uppercased() {
    // "dbc" → "DBC" with double-quote wrapping
    assert_eq!(quote_identifier("dbc"), "\"DBC\"");
}

// TC-046-001-B: all-lowercase table name
#[test]
fn test_quote_identifier_table_lowercase_uppercased() {
    assert_eq!(quote_identifier("tables"), "\"TABLES\"");
}

// TC-046-001-C: mixed-case input fully uppercased
#[test]
fn test_quote_identifier_mixed_case_uppercased() {
    assert_eq!(quote_identifier("TablesV"), "\"TABLESV\"");
}

// TC-046-001-D: already-uppercase input stays uppercase (idempotent)
#[test]
fn test_quote_identifier_uppercase_idempotent() {
    assert_eq!(quote_identifier("EMPLOYEES"), "\"EMPLOYEES\"");
}

// TC-046-001-E: embedded double quote is escaped AFTER uppercasing
// Input: my"table → upper → MY"TABLE → escape → MY""TABLE → wrap → "MY""TABLE"
#[test]
fn test_quote_identifier_embedded_quote_escaped_after_uppercase() {
    assert_eq!(quote_identifier("my\"table"), "\"MY\"\"TABLE\"");
}

// TC-046-001-F: identifier with space — uppercased
#[test]
fn test_quote_identifier_space_uppercased() {
    assert_eq!(quote_identifier("my table"), "\"MY TABLE\"");
}

// TC-046-001-G: qualified pair via quote_qualified_name — both parts uppercased
#[test]
fn test_quote_qualified_name_both_parts_uppercased() {
    assert_eq!(quote_qualified_name("dbc", "tables"), "\"DBC\".\"TABLES\"");
}

// TC-046-001-H: qualified name with mixed case — both uppercased
#[test]
fn test_quote_qualified_name_mixed_case_uppercased() {
    assert_eq!(quote_qualified_name("MyDb", "TablesV"), "\"MYDB\".\"TABLESV\"");
}

// TC-046-001-I: SQL injection still blocked — quotes doubled after uppercase
#[test]
fn test_quote_identifier_injection_still_blocked_after_uppercase() {
    let malicious = "employees; DROP TABLE users; --";
    // The input is uppercased and the whole string is wrapped in a single quoted identifier
    let result = quote_identifier(malicious);
    // Must start and end with double quote, no unescaped SQL
    assert!(result.starts_with('"'));
    assert!(result.ends_with('"'));
    // Must contain the uppercased version of the content
    assert!(result.contains("EMPLOYEES"));
}

// TC-046-001-J: empty string — unchanged behaviour (empty uppercased = empty)
#[test]
fn test_quote_identifier_empty_unchanged() {
    assert_eq!(quote_identifier(""), "\"\"");
}
```

## Pass/Fail Criteria

**PASS if:**
- All 10 tests compile and pass
- Identifiers are uppercased before being wrapped in double quotes
- Embedded double quotes are still doubled (SQL injection protection preserved)
- Empty input returns `""`

**FAIL if:**
- Any test fails — indicates the uppercase behavior was not implemented or is incorrect
- Embedded quote escaping was broken by the uppercase change
- `quote_qualified_name` does not uppercase both parts

## Notes

- These tests REPLACE the existing `test_quote_identifier_simple` assertion which expected `"employees"` (lowercase). The new behavior makes `"employees"` → `"EMPLOYEES"`. The existing test will need to be updated by the implementer.
- The existing doc-comment examples in `identifiers.rs` that assert lowercase output must also be updated by the implementer — they are test code that will break.
- Unicode identifiers (Chinese, Cyrillic, etc.): `to_uppercase()` in Rust follows Unicode standard. The test suite for Unicode is separate and those tests assert the correct Unicode uppercase form.
