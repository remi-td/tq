# TC-040-001: Variable Substitution Engine - Unit Tests

**Sprint:** 40
**Feature:** Variable Substitution Engine
**Type:** Unit Tests
**Location:** `src/params.rs` - `#[cfg(test)] mod tests`
**Framework:** Built-in Rust test framework (`#[test]`)

## Overview

These unit tests validate the core variable substitution engine: YAML parsing, marker scanning, value resolution, multi-file merging, and error handling. All tests run without a database connection.

---

## YAML Parsing Tests

### TC-040-001-001: Parse flat YAML

**Name:** `test_parse_yaml_simple_flat`

**Input:**
```yaml
table: employees
schema: hr
```

**Expected:** Flat map with entries `table → "employees"` and `schema → "hr"`

**Asserts:**
- `params.get("table")` == `Some("employees")`
- `params.get("schema")` == `Some("hr")`

---

### TC-040-001-002: Parse two-level nested YAML

**Name:** `test_parse_yaml_nested_two_levels`

**Input:**
```yaml
target:
  db: mydb
```

**Expected:** Key `target.db` resolves to `"mydb"`

**Asserts:**
- `params.get("target.db")` == `Some("mydb")`

---

### TC-040-001-003: Parse three-level nested YAML

**Name:** `test_parse_yaml_nested_three_levels`

**Input:**
```yaml
target:
  database:
    prefix: PROD
```

**Expected:** `{{target.database.prefix}}` resolves to `"PROD"`

**Asserts:**
- After substitution of `"SELECT {{target.database.prefix}}"` → `"SELECT PROD"`

---

### TC-040-001-004: Integer YAML value coerced to string


**Asserts:**

## Variable Resolution Tests

### TC-040-001-009: Simple marker substitution

**Name:** `test_substitute_simple_variable`

**Input SQL:** `"SELECT * FROM {{schema}}.{{table}}"`

**Params:** `{ schema: hr, table: employees }`

**Expected:** `"SELECT * FROM hr.employees"`

### TC-040-001-010: Nested path marker substitution

**Name:** `test_substitute_nested_path`

**Input SQL:** `"FROM {{target.db}}.{{target.schema}}.{{target.table}}"`

**Params:**
```yaml
target:
  db: mydb
  schema: hr
  table: employees
```

**Expected:** `"FROM mydb.hr.employees"`

---

### TC-040-001-011: Multiple markers in one SQL

## Multi-File Merge Tests

### TC-040-001-020: Merge two non-overlapping files

**Name:** `test_merge_two_files_non_overlapping`

**File A:** `{ table: employees }`
**File B:** `{ schema: hr }`

**Expected:** Merged map contains both `table → "employees"` and `schema → "hr"`

---

### TC-040-001-021: Later file overrides earlier on conflict

**Name:** `test_merge_override_later_wins`

**File A (first):** `{ env: staging }`
**File B (second):** `{ env: production }`

**Expected:** After merge, `env` → `"production"` (file B wins)

---

### TC-040-001-022: Three files - last definition always wins

**Name:** `test_merge_three_files_priority`

**File A:** `{ x: a }`
**File B:** `{ x: b }`
**File C:** `{ x: c }`

**Merge order:** A, B, C

**Expected:** `x` → `"c"`

---

### TC-040-001-023: Nested key override from later file

**Name:** `test_merge_nested_override`

**File A:**
```yaml
target:
  db: staging_db
  schema: staging
```

**File B:**
```yaml
target:
  db: prod_db
```

**Expected (deep merge):** `target.db` → `"prod_db"`, `target.schema` remains `"staging"` if deep merge is implemented; OR `target.db` → `"prod_db"` and `target.schema` → undefined if shallow (top-level key) merge.

**Note:** The expected merge behavior (deep vs shallow) is an implementation decision. This test documents that override must work for at least the top-level replacement case. The exact assertion will be written to match the implementation once specified.
