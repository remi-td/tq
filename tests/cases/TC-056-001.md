## Purpose

Verify that the pagination logic for `tq query` correctly slices `QueryResult` rows, produces accurate JSON envelope metadata, handles all output formats, and enforces error conditions — all without a live database.

## Acceptance Criteria Coverage

- PAG-REQ-1: `--page-size N` slices results to N rows
- PAG-REQ-2: `--page P` selects 1-based page (default = 1)
- PAG-REQ-3: JSON envelope includes `page`, `page_size`, `has_more`, `total_rows` when paginated
- PAG-REQ-4: `has_more=true` when more pages exist, `false` on last page
- PAG-REQ-5: Without `--page-size`, output is unchanged (backward compatible)
- PAG-REQ-6: Table, JSON, CSV, markdown formats all supported
- PAG-REQ-8: `--page` without `--page-size` produces error

## Scope

This test validates:
1. Page 1 slicing (rows 0..page_size)
2. Page 2 slicing (rows page_size..2*page_size)
3. Last page slicing (returns remaining rows, fewer than page_size)
4. Page beyond last (empty result or error)
5. `has_more=true` for non-last pages
6. `has_more=false` for last page
7. `total_rows` equals full result set size
8. `row_count` in envelope equals slice size (not total)
9. No pagination fields in envelope when `--page-size` absent (backward compat)
10. Table format footer: "Page X of Y (Z total rows)"
11. CSV: pagination metadata either in footer comment or omitted (format-specific)
12. Markdown: pagination footer line
13. Error: `--page` supplied without `--page-size`
14. Error: `--page-size` and `--limit` supplied together

## Prerequisites

- `cargo test --lib` available
- Pagination logic implemented in `src/format/json.rs` and/or `src/commands/query.rs`
- `PaginationOptions` struct (or equivalent) implemented

## Test Procedure

### Location

Tests should be co-located in the module that implements pagination logic. If pagination is a `PaginationOptions` struct + a `apply_pagination()` function in `src/format/json.rs`, tests go in that file's `#[cfg(test)]` block. If pagination slicing lives in `src/commands/query.rs`, tests go there.

### Execution Command

```bash
cargo test --lib pagination 2>&1
```

Or to run all unit tests including pagination:

```bash
cargo test --lib 2>&1
```

### Test Implementations

The rust-teradata-architect will implement these tests as part of the feature. The following are the exact scenarios each test must cover:

#### Test Group A: JSON Envelope Pagination Metadata

**Test A1: `test_json_pagination_page1_envelope`**
- Setup: QueryResult with 15 rows, PaginationOptions { page_size: 5, page: 1 }
- Call: paginated JSON write function
- Assert:
  - `parsed["pagination"]["page"] == 1`
  - `parsed["pagination"]["page_size"] == 5`
  - `parsed["pagination"]["total_rows"] == 15`
  - `parsed["pagination"]["has_more"] == true`
  - `parsed["row_count"] == 5`
  - `parsed["data"].len() == 5`
  - data contains rows 0..4 (first 5)

**Test A2: `test_json_pagination_page2_envelope`**
- Setup: QueryResult with 15 rows, PaginationOptions { page_size: 5, page: 2 }
- Assert:
  - `parsed["pagination"]["page"] == 2`
  - `parsed["pagination"]["has_more"] == true`
  - `parsed["row_count"] == 5`
  - data contains rows 5..9 (second 5)

**Test A3: `test_json_pagination_last_page_envelope`**
- Setup: QueryResult with 15 rows, PaginationOptions { page_size: 5, page: 3 }
- Assert:
  - `parsed["pagination"]["page"] == 3`
  - `parsed["pagination"]["has_more"] == false`
  - `parsed["row_count"] == 5`
  - data contains rows 10..14 (last 5)

**Test A4: `test_json_pagination_partial_last_page`**
- Setup: QueryResult with 13 rows, PaginationOptions { page_size: 5, page: 3 }
- Assert:
  - `parsed["pagination"]["has_more"] == false`
  - `parsed["pagination"]["total_rows"] == 13`
  - `parsed["row_count"] == 3` (only 3 rows on last page)
  - `parsed["data"].len() == 3`

**Test A5: `test_json_pagination_beyond_last_page`**
- Setup: QueryResult with 10 rows, PaginationOptions { page_size: 5, page: 5 }
- Assert: either returns empty data with `has_more=false` and `total_rows=10`, OR returns a non-zero error code
- Note: document which behavior is chosen

**Test A6: `test_json_no_pagination_backward_compat`**
- Setup: QueryResult with 10 rows, no PaginationOptions (or None)
- Call: existing `write()` or `write_with_metadata()` function without pagination params
- Assert:
  - `parsed["ok"] == true`
  - `parsed["row_count"] == 10`
  - `parsed["data"].len() == 10`
  - `parsed.get("pagination")` is None (field must not appear)

**Test A7: `test_json_page1_default`**
- Setup: QueryResult with 8 rows, PaginationOptions { page_size: 5, page: 1 } (page defaults to 1)
- Assert: same as A1, confirms default page=1 behavior

#### Test Group B: Table Format Footer

**Test B1: `test_table_format_pagination_footer`**
- Setup: QueryResult with 20 rows, page_size=5, page=2 (table format)
- Call: table format render with pagination options
- Assert: output string contains "Page 2 of 4" or "Page 2 of 4 (20 total rows)"

**Test B2: `test_table_format_no_pagination_no_footer`**
- Setup: QueryResult with 20 rows, no pagination
- Assert: output does NOT contain "Page" as a footer line

#### Test Group C: CSV Format

**Test C1: `test_csv_pagination_does_not_break_format`**
- Setup: QueryResult with 10 rows, page_size=3, page=2, CSV format
- Assert: output is valid CSV with exactly 3 data rows plus header; no pagination fields embedded in CSV data rows

#### Test Group D: Markdown Format

**Test D1: `test_markdown_pagination_footer`**
- Setup: QueryResult with 10 rows, page_size=5, page=1, markdown format
- Assert: output contains markdown table with 5 data rows AND a footer line matching "Page 1 of 2" pattern

#### Test Group E: Error Cases

**Test E1: `test_error_page_without_page_size`**
- Approach: Validate CLI argument parsing (or the execute function) returns an error when `--page` is supplied but `--page-size` is absent
- Implementation note: This may be tested at the CLI args validation layer (`src/cli.rs`) or at command execution layer
- Assert: returns `Err(...)` with message containing "page-size" (case-insensitive)

**Test E2: `test_error_page_size_and_limit_together`**
- Approach: Validate CLI args or execute function returns error when both `--page-size` and `--limit` are provided
- Assert: returns `Err(...)` with message indicating mutual exclusion

## Expected Results

All unit tests pass. No live database required.

## Pass/Fail Criteria

**PASS if:**
- All 14+ test functions compile and pass
- JSON envelope fields match specifications exactly
- Slicing is accurate (off-by-one-free)
- Backward compatibility confirmed (no pagination fields when not used)
- Error conditions return meaningful error messages

**FAIL if:**
- Any test panics or fails an assertion
- `pagination` field appears in non-paginated output
- `has_more` value is inverted
- `total_rows` reflects page size instead of full result count
- Error cases do not return errors

## Notes

- All tests use writer-injection (`Vec<u8>` as writer), consistent with existing `src/format/json.rs` pattern
- `create_test_result_n(n: usize)` helper should be created to build a QueryResult with `n` distinguishable rows
- Rows should have a unique identifier field (e.g., `id: 0, 1, 2, ...`) to verify correct slice
- Test A5 (beyond last page) behavior should be documented and made consistent with spec
- Integration tests for CLI end-to-end are in TC-056-002 (`#[ignore]`)
