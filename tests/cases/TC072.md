# Test Case TC072: Tab Completion - Qualified Name Completion (database.table)

## Purpose

Verify that tab completion correctly handles Teradata's qualified naming convention (database.table format) and shows tables from the specified database when user types "database."

This is critical for Teradata where qualified names are standard practice.

## Scope

**Testing:**
- Completion after "database." pattern
- Shows tables from that specific database
- Not tables from current database
- Multiple database completion
- Case sensitivity handling

**Not Testing:**
- Unqualified table completion (TC071)
- Column completion (TC073)
- Performance/caching

## Prerequisites

- tq REPL connected to Teradata
- At least 2 databases accessible (e.g., production, staging)
- Each database has at least 3 tables
- User has SELECT on DBC.TablesV
- Database names known ahead of test

## Test Procedure

### Setup

```bash
./target/release/tq repl

# Identify available databases
tq> SELECT DISTINCT DatabaseName FROM DBC.TablesV
    WHERE DatabaseName NOT IN ('DBC', 'SYSLIB')
    ORDER BY DatabaseName;

# Note: Record database names for use in test
# Example: production, staging, development
```

### Execution Steps

**Step 1: Complete database name first**

```sql
tq> SELECT * FROM prod<TAB>
```

**Expected outcome:**
- Auto-completes to "production" (if unique match)
- OR shows list: production, prod_archive, etc. (if multiple)
- User sees database names, not table names yet

**Step 2: Complete tables after database prefix**

```sql
tq> SELECT * FROM production.<TAB>
```

**Expected outcome:**
- Shows "Loading tables in 'production'..." (if first time)
- Displays list of tables from production database ONLY
- Does NOT show tables from current database
- Format: just table names (not database.table)

**Example expected output:**
```
Tables in 'production':
  customers    employees    orders    products    departments
```

**Step 3: Verify different database completion**

```sql
tq> SELECT * FROM staging.<TAB>
```

**Expected outcome:**
- Shows tables from staging database
- Different list than production (unless identical schema)
- Context switches correctly between databases

**Step 4: Test partial qualified table name**

```sql
tq> SELECT * FROM production.emp<TAB>
```

**Expected outcome:**
- Filters to tables starting with "emp" in production
- If single match: auto-completes to "production.employees"
- If multiple: shows filtered list

**Step 5: Test in JOIN clause**

```sql
tq> SELECT * FROM employees e
    JOIN production.<TAB>
```

**Expected outcome:**
- Shows production database tables
- Context detection works in JOIN
- Same behavior as FROM

**Step 6: Test case variations**

```sql
tq> SELECT * FROM Production.<TAB>
tq> SELECT * FROM PRODUCTION.<TAB>
tq> SELECT * FROM production.<TAB>
```

**Expected outcome:**
- All three show same table list
- Case-insensitive database matching
- Teradata default behavior

### Verification

**Validation Checklist:**

- [ ] Database name completion works
- [ ] Tables shown match specified database
- [ ] Context switches correctly per database
- [ ] Partial table prefix filters within database
- [ ] Qualified names complete correctly
- [ ] Case-insensitive matching works

**Correctness Validation:**

Cross-check completion against actual database:
```sql
tq> SELECT TableName FROM DBC.TablesV
    WHERE DatabaseName = 'production'
    ORDER BY TableName;
```

Compare output to Tab completion list - should match exactly.

### Cleanup

```bash
tq> /quit
```

Tables in 'production':

**Step 4 Output (single match):**

```

```

**Step 4 Output (multiple matches):**

```
tq> SELECT * FROM production.emp<TAB>

  employees    employee_archive    employee_history
```

## Pass/Fail Criteria

**PASS:**
- Database name completion works
- "database.<TAB>" shows tables from that database
- Tables shown are from specified database, not current
- Partial qualified names complete correctly
- Multiple databases handled independently
- Case-insensitive matching works
- Context detection robust in FROM/JOIN

**FAIL:**
- "database.<TAB>" shows current database tables (wrong context)
- "database.<TAB>" shows keywords or garbage
- Cannot complete qualified names
- Tables from wrong database shown
- Case sensitivity broken
- Completion empty when tables exist

## Notes

**Why This Test is Critical:**

Teradata heavily uses qualified names (database.table):
- Cross-database queries are common
- Qualified names avoid ambiguity
- Users expect this to work smoothly

Sprint 11 bug may have broken this specifically because:
- Context parsing failed to recognize "database." pattern
- Fell back to generic SQL keywords
- Teradata-specific completion logic not tested

**Implementation Detail to Test:**

The completion engine must:
1. Detect "database." pattern via regex
2. Extract database name from pattern
3. Query DBC.TablesV filtered by that database
4. Show tables from that database only
5. Handle database name completion first (before dot)

**Edge Cases to Consider:**

- Database name with underscore: `prod_db.`
- Database name with numbers: `db2.`
- Non-existent database: `fake_db.` (should show error or empty)
- Permission denied database (should show helpful error)

**Reference:**
- Teradata naming: database.table (not schema.table like PostgreSQL)
- Specifications: detailed-specifications/repl-mode.md#table-name-completion
- Sprint 8 redesign documented qualified name handling
