# Test Case TC047: Table Formatting - Very Long Values and Truncation

## Purpose

Verify that tables handle very long column values gracefully, either by truncation with indicators or intelligent wrapping, without breaking alignment or causing excessive horizontal scrolling.

## Scope

**Testing:**
- Long string values (100+ characters)
- Column width constraints
- Truncation indicators (e.g., "...")
- Alignment preservation with long values
- Terminal width limits

**Not Testing:**
- Paging (covered in TC057-TC063)
- Very wide tables (many columns - covered in TC045)
- NULL handling

## Prerequisites

- tq REPL mode active
- Live Teradata database connection
- Ability to construct test queries with long strings

## Test Procedure

### Setup

```bash
# Start tq in REPL mode
./target/release/tq

# Note terminal width
tput cols
```

### Execution Steps

**Step 1: Query with long VARCHAR values**

```sql
tq> SELECT
    'Short' AS short_col,
    'This is a very long string value that exceeds typical column width and should be handled gracefully by the table formatter without breaking alignment' AS long_col,
    'End' AS end_col;
```

**Expected outcome:**
- Table renders without hanging
- Long column either:
  - Truncates with "..." indicator, OR
  - Wraps within column, OR
  - Expands but respects max column width constraint
- Alignment with other columns is maintained
- Table fits within terminal width or clearly indicates overflow

**Step 2: Test with multiple long values**

```sql
tq> SELECT TOP 3
    DatabaseName,
    CAST(REPEAT('A', 200) AS VARCHAR(200)) AS long_value_1,
    CAST(REPEAT('B', 150) AS VARCHAR(150)) AS long_value_2,
    PermSpace
    FROM DBC.DatabasesV;
```

**Expected outcome:**
- Both long columns are handled consistently
- Table remains readable
- Columns don't push each other off screen
- Alignment is preserved

**Step 3: Test with realistic long data (SQL queries)**

```sql
tq> SELECT TOP 5
    TableName,
    RequestText
    FROM DBC.TablesV
    WHERE TableKind = 'V'
    AND RequestText IS NOT NULL;
```

Note: `RequestText` contains view definitions and can be very long (1000+ chars).

**Expected outcome:**
- RequestText column handles long SQL gracefully
- Other columns (TableName) remain readable
- Table is usable despite one very wide column

**Step 4: Test terminal width constraint**

```sql
tq> SELECT
    CAST('Col1' AS VARCHAR(50)) AS c1,
    CAST(REPEAT('X', 100) AS VARCHAR(100)) AS very_long,
    CAST('Col3' AS VARCHAR(50)) AS c3;
```

**Expected outcome:**
- Table detects terminal width
- Long column is constrained or clearly marked as truncated
- Table doesn't force horizontal scrolling for 3 columns

### Verification

**Key Checks:**

1. **Truncation Behavior:**
   - [ ] Long values are handled (not causing crashes/hangs)
   - [ ] If truncated, clear indicator present (e.g., "...", "→")
   - [ ] Truncation is consistent across all long values

2. **Column Width Constraints:**
   - [ ] NO column exceeds 80 characters (or max_column_width setting)
   - [ ] Long values don't cause unbounded column growth
   - [ ] Terminal width is respected

3. **Alignment Preservation:**
   - [ ] Headers still align with data despite long values
   - [ ] Vertical separators remain straight
   - [ ] Other columns are not affected by one long column

4. **Readability:**
   - [ ] Can still identify column headers
   - [ ] Can read non-long columns easily
   - [ ] Long column is at least partially readable
   - [ ] Clear indication if more data exists (truncation indicator)

5. **Performance:**
   - [ ] Table renders in <2 seconds even with long values
   - [ ] No visible lag or hanging

**Truncation Indicator Check:**

If truncation occurs, verify indicator:
- Common patterns: "...", "…", "→", "[truncated]"
- Indicator should be at end of truncated value
- Example: "This is a very long string val..." (note "..." at end)

### Cleanup

```sql
tq> /quit
```

```

**Key Characteristics:**
- long_col is truncated to fit terminal width
- "..." indicator shows there's more data
- Alignment is maintained
- Other columns are readable

**Option 2: Column Width Constraint**

```
╭───────────┬────────────────────────────────────────────────┬──────╮
│ short_col ┆ long_col                                       ┆ end_col │
╞═══════════╪════════════════════════════════════════════════╪════════╡

**Key Characteristics:**

**Anti-Pattern (Should NOT Occur):**

```
╭───────────┬──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┬──────╮
│ short_col ┆ long_col                                                                                                                                                                     ┆ end_col │

╰───────────┴──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┴────────╯
```

This shows unbounded column growth (200+ characters), making table unusable.

## Pass/Fail Criteria

**PASS:**
- Long values (100+ chars) are handled gracefully
- Column width is constrained (≤80 chars per column, or max_column_width)
- If truncated, clear indicator present
- Alignment is maintained
- Table renders in <2 seconds
- Table fits in terminal or clearly indicates horizontal scroll needed

**FAIL:**
- Long values cause crashes or hangs
- Columns grow unbounded (>100 chars)
- No truncation indicator when data is cut off
- Alignment breaks with long values
- Table renders in >5 seconds
- Horizontal scrolling required for 3-column table

## Notes

**Configuration Context:**

In `src/format/table.rs`, there may be a `max_column_width` setting. The fix should:
1. Respect this setting per-column (not multiply by column count)
2. Apply truncation when values exceed max_column_width
3. Add truncation indicator when truncation occurs

**Teradata Context:**

Common long-value columns in Teradata:
- `RequestText` in DBC.TablesV (view definitions, 1000+ chars)
- `CommentString` in various DBC tables (can be 255+ chars)
- SQL query text in DBC.QryLog* tables

Users need to see these columns without breaking the table layout.

**User Experience:**

When truncation occurs, users should:
1. See that data is truncated (via indicator)
2. Know they can use JSON format for full values: `--format json`
3. Still be able to read other columns easily

**Alternative Solutions:**

If truncation is not implemented, acceptable alternatives:
1. Wrapping text within column (multi-line cell)
2. Horizontal paging (covered in TC059-TC060)
3. Smart ellipsis in middle of long values (e.g., "Start...End")
