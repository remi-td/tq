# Test Case TC076: Table Display - Terminal Width Detection and Column Truncation (80 cols)

## Purpose

Verify that table display correctly detects terminal width and truncates columns to fit in a standard 80-column terminal, showing "(+n cols)" indicator for hidden columns.

This tests the core Sprint 11 Bug 1 fix - simpler column truncation replacing broken padding.

## Scope

**Testing:**
- Terminal width detection (80 columns)
- Column truncation when too many columns
- "(+n cols)" indicator in header
- "..." indicator in body rows
- Footer with hidden column names
- Table remains readable
- All columns fit within terminal

**Not Testing:**
- Other terminal widths (separate TCs)
- TTY vs batch mode (TC080)
- Performance

## Prerequisites

- tq binary built with Sprint 11 fixes
- Terminal set to exactly 80 columns wide
- Teradata connection available
- Test query with 10+ columns available

## Test Procedure

### Setup

```bash
# Set terminal to exactly 80 columns
# (Method varies by terminal emulator)
# - iTerm2: Profiles > Window > Columns = 80
# - Terminal.app: Window Settings > Columns = 80
# - Can verify with: tput cols

# Verify terminal width
tput cols
# Should output: 80

# Start REPL
./target/release/tq repl
```

### Execution Steps

**Step 1: Execute query with many columns (10+ columns)**

```sql
tq> SELECT TOP 5
    DatabaseName,
    TableName,
    CreatorName,
    OwnerName,
    RequestText,
    TableKind,
    ProtectionType,
    JournalFlag,
    CreatorName,
    RequestTxtOverflow
  FROM DBC.TablesV
  ORDER BY DatabaseName;
```

**Expected outcome:**
- Table displays with subset of columns (leftmost 3-5 columns)
- Remaining columns hidden
- "(+n cols)" indicator in header row
- "..." indicator in last visible column of body rows
- Table fits within 80 characters width
- No horizontal scrolling required
- No text wrapping

**Step 2: Count visible columns**

Observe the output and count:
- How many columns are visible?
- Expected: 3-5 columns depending on column width

**Expected outcome:**
- Reasonable number of columns shown (prioritizes readability)
- Not all 10 columns crammed (would be unreadable)
- Not just 1 column (too conservative)

**Step 3: Verify "(+n cols)" indicator in header**

Look at the rightmost column in header row:

**Expected format:**
```
┆ (+6 cols) │
```

OR

```
│ (+6) │
```

**Expected outcome:**
- Indicator shows number of HIDDEN columns
- If 4 visible out of 10 total: shows "+6"
- Indicator positioned in header row
- Clear visual separation from data

**Step 4: Verify "..." indicator in body rows**

Look at the rightmost column in each data row:

**Expected format:**
```
┆ ...       │
```

**Expected outcome:**
- Each body row shows "..." in last visible column
- Consistent placement across all rows
- Indicates "more data exists but hidden"

**Step 5: Verify footer with hidden column names**

Look at footer area below table:

**Expected format:**
```
5 rows returned

Hidden columns: RequestText, TableKind, ProtectionType, JournalFlag, RequestTxtOverflow
```

OR

```
Hidden columns (5): RequestText, TableKind, ProtectionType, JournalFlag, RequestTxtOverflow
```

**Expected outcome:**
- Lists names of hidden columns
- User knows what data exists but isn't shown
- Can adjust query if needed

**Step 6: Measure actual width**

Copy a table row and count characters:

```bash
# Paste row into: wc -c
# Or count manually with ruler
```

**Expected outcome:**
- Total width ≤ 80 characters
- Slight overflow acceptable (82-83 chars) due to borders
- No excessive overflow (>85 chars = fail)

**Step 7: Test readability**

**Expected outcome:**
- Column headers readable
- Data values readable
- Alignment preserved
- No excessive truncation making values useless

## Pass/Fail Criteria

**PASS:**
- Table fits within 80 columns (≤83 with borders)
- Shows reasonable subset of columns (3-5)
- "(+n cols)" indicator present and accurate
- "..." indicators in body rows
- Footer lists hidden column names
- Table is readable and professionally formatted
- Headers align with data
- No excessive padding or scattering

**FAIL:**
- Table exceeds 80 columns significantly (>85 chars)
- Horizontal scrolling required
- Text wraps to next line
- All columns crammed unreadably
- No indication of hidden columns
- Scattered/broken layout like bug screenshot
- Headers misaligned from data
- Excessive padding (>3x data length)

## Notes

**Design Goal:**

Sprint 11 simplifies table display:
- OLD: Complex padding logic (kept breaking)
- NEW: Simple terminal width detection + truncation

**Algorithm:**
1. Detect terminal width (80 cols)
2. Calculate which columns fit
3. Show leftmost N columns that fit
4. Add "(+X cols)" indicator column
5. Show "..." in body rows
6. List hidden columns in footer

**Why 80 Columns:**

80-column terminals are common:
- Default in many terminal emulators
- Standard for decades
- Minimum reasonable width
- Good test case for truncation logic

Wider terminals tested in TC077, TC078, TC079.

**Implementation Detail:**

Use `terminal_size` crate:
```rust
if let Some((Width(w), Height(h))) = terminal_size() {
    // w is terminal width in chars
    // Truncate columns to fit in w
}
```

**Visual Validation Critical:**

This test REQUIRES human inspection:
- Automated tests can check width
- Can't easily validate "looks good"
- Screenshots recommended in test results
