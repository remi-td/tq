## Purpose

Verify that all Sprint 46 /inspect formatting acceptance criteria are met by testing the formatting helpers in `src/commands/inspect.rs` directly. All helpers are pure functions or write to `impl Write`; no database connection is needed.

## Acceptance Criteria Coverage

- **AC-1**: Section headers use `── Section Name ──` format
- **AC-2**: Default column shows `-` instead of empty string
- **AC-3**: Column count footer: `N columns` after column table
- **AC-4**: Skew interpretation hint: `(low)`, `(moderate)`, `(high)` after skew percentage
- **AC-5**: `O` TableKind mapped to "Table (NoPI)" instead of "Table"
- **AC-6**: Error message uses `Error:` prefix for not-found
- **AC-7**: Usage prompt shows examples when `/inspect` called with no argument
- **AC-8**: Direct row indexing fixed (no panic on empty result sets)

## Prerequisites

- `src/commands/inspect.rs` has all 8 formatting changes applied
- `cargo test --lib` compiles successfully

## Test Procedure

### Test Implementation (in `src/commands/inspect.rs` `#[cfg(test)]` module)

Extend the existing `#[cfg(test)]` module with the following tests:

```rust
// =========================================================================
// Sprint 46: Formatting compliance tests
// =========================================================================

// TC-046-007-A: AC-5 — TableKind "O" maps to "Table (NoPI)"
#[test]
fn test_map_table_kind_o_is_nopi() {
    assert_eq!(map_table_kind("O"), "Table (NoPI)");
}

// TC-046-007-B: AC-5 regression — TableKind "T" still maps to "Table"
#[test]
fn test_map_table_kind_t_still_table() {
    assert_eq!(map_table_kind("T"), "Table");
}

// TC-046-007-C: AC-4 — Skew hint boundaries
// Boundary spec: 0–5% = low, 6–20% = moderate, >20% = high
#[test]
fn test_skew_hint_low() {
    assert_eq!(skew_hint(0.0), "(low)");
    assert_eq!(skew_hint(5.0), "(low)");
}

#[test]
fn test_skew_hint_moderate() {
    assert_eq!(skew_hint(5.1), "(moderate)");
    assert_eq!(skew_hint(20.0), "(moderate)");
}

#[test]
fn test_skew_hint_high() {
    assert_eq!(skew_hint(20.1), "(high)");
    assert_eq!(skew_hint(100.0), "(high)");
}

// TC-046-007-D: AC-1 — Section header format
// Spec: `── Section Name ──`
#[test]
fn test_section_header_format() {
    // The section header must use box-drawing character ─ (U+2500)
    // and follow the pattern: ── <Name> ──
    let header = format_section_header("Object Info");
    assert!(
        header.contains("──"),
        "Section header must contain ── (box-drawing chars)\nGot: {}",
        header
    );
    assert!(
        header.contains("Object Info"),
        "Section header must contain the section name\nGot: {}",
        header
    );
    assert!(
        !header.contains("==="),
        "Section header must NOT use === style\nGot: {}",
        header
    );
}

// TC-046-007-E: AC-2 — Default column shows "-" for None
#[test]
fn test_default_display_none_shows_dash() {
    let display = display_default(None);
    assert_eq!(display, "-", "None default must render as '-'");
}

// TC-046-007-F: AC-2 regression — Default column shows value when Some
#[test]
fn test_default_display_some_shows_value() {
    let display = display_default(Some("42"));
    assert_eq!(display, "42", "Some default must render the value");
}

#[test]
fn test_default_display_some_empty_string() {
    // An explicitly set empty default is different from None
    let display = display_default(Some(""));
    assert_eq!(display, "", "Empty string default must render as empty, not '-'");
}

// TC-046-007-G: AC-3 — Column count footer "N columns"
// Test that the footer is rendered after the column table
#[test]
fn test_column_count_footer_rendered() {
    use std::io::Write;
    // Construct minimal column data
    let columns = vec![
        ColumnInfo {
            name: "col1".to_string(),
            col_type: "VARCHAR(100)".to_string(),
            nullable: "YES".to_string(),
            default: None,
        },
        ColumnInfo {
            name: "col2".to_string(),
            col_type: "INTEGER".to_string(),
            nullable: "NO".to_string(),
            default: Some("0".to_string()),
        },
        ColumnInfo {
            name: "col3".to_string(),
            col_type: "DATE".to_string(),
            nullable: "YES".to_string(),
            default: None,
        },
    ];

    let mut output = Vec::new();
    render_columns_section(&columns, &mut output).expect("render_columns_section failed");
    let rendered = String::from_utf8(output).expect("Invalid UTF-8");

    assert!(
        rendered.contains("3 columns"),
        "Expected '3 columns' footer in rendered output\nGot: {}",
        rendered
    );
}

// TC-046-007-H: AC-6 — Not-found error uses "Error:" prefix
#[test]
fn test_not_found_error_has_error_prefix() {
    let mut output = Vec::new();
    render_not_found_error("mydb.mytable", &mut output).expect("render failed");
    let rendered = String::from_utf8(output).expect("Invalid UTF-8");

    assert!(
        rendered.contains("Error:"),
        "Not-found message must start with 'Error:'\nGot: {}",
        rendered
    );
}

// TC-046-007-I: AC-7 — Usage prompt contains examples when no argument given
#[test]
fn test_usage_prompt_contains_examples() {
    let mut output = Vec::new();
    render_usage_prompt(&mut output).expect("render failed");
    let rendered = String::from_utf8(output).expect("Invalid UTF-8");

    // Must contain at least one usage example
    assert!(
        rendered.contains("/inspect") || rendered.contains("inspect"),
        "Usage prompt must contain 'inspect' example\nGot: {}",
        rendered
    );
    assert!(
        rendered.contains("Usage") || rendered.contains("Example"),
        "Usage prompt must contain Usage or Example\nGot: {}",
        rendered
    );
}

// TC-046-007-J: AC-8 — Safe row indexing (no panic on empty result)
// Verify that accessing rows from an empty result set uses .get() not direct indexing
// This is a compile-time + behavior test: we simulate what previously caused panics
#[test]
fn test_safe_row_access_empty_result_no_panic() {
    // Simulate what happens when DBC query returns 0 rows
    // Previously: result.rows[0] would panic
    // After fix: result.rows.get(0) returns None gracefully
    let rows: Vec<Vec<crate::db::Value>> = vec![];

    // This must not panic:
    let first = rows.get(0);
    assert!(first.is_none(), "Empty rows get(0) must return None");

    // Simulate the nested access pattern:
    let col_val = rows.get(0).and_then(|row| row.first());
    assert!(col_val.is_none(), "Safe nested access must return None, not panic");
}
```

## Pass/Fail Criteria

**PASS if:**
- All 15 tests compile and pass
- `map_table_kind("O")` returns `"Table (NoPI)"` (not `"Table"`)
- `skew_hint` returns the correct label for each boundary
- Section header format uses `──` (not `===`)
- `None` default renders as `"-"`
- Column count footer appears
- Error message has `"Error:"` prefix
- Usage prompt has examples
- Empty result set access does not panic

**FAIL if:**
- `map_table_kind("O")` still returns `"Table"` — AC-5 not fixed
- Section header still uses `===` — AC-1 not fixed

## Notes

- Several helper functions tested here (`skew_hint`, `format_section_header`, `display_default`, `render_columns_section`, `render_not_found_error`, `render_usage_prompt`) are **new** functions that the implementer must extract from the existing inline rendering code. Currently the rendering logic is embedded in `inspect_object()`. The implementer should refactor to make these helpers testable.
- If the implementer chooses not to extract helpers but instead tests via writer injection into `inspect_object()` with a mock `DatabaseClient`, the test implementations above should be adapted accordingly.
- `ColumnInfo` struct is already defined in `inspect.rs`; it can be used directly in tests within the same file.
- Skew boundary thresholds (5%, 20%) are derived from common Teradata conventions. The exact thresholds should match the specification from `docs/specifications/`.
- The `test_safe_row_access_empty_result_no_panic` test validates the AC-8 fix conceptually. The actual fix is in the production code path; this test verifies the safe pattern. A real panic regression test would require calling `query_object_type` with a result set, which requires DB access.
