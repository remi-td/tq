# Test Case TC071: Tab Completion - Context-Aware Database/Table Completion After FROM

## Purpose

Verify that tab completion after FROM/JOIN keywords shows context-aware completions (databases and tables), NOT generic "(SQL keyword)" repeated 25 times.

This test directly validates the Sprint 11 Bug 2 fix - the regression where completion showed SQL keywords instead of actual database objects.

## Scope

**Testing:**
- Tab completion triggers after FROM keyword
- Shows databases + tables from current database
- Does NOT show generic "SQL keyword" repeated
- Context detection works correctly
- Live database metadata used

**Not Testing:**
- Column completion (TC073)
- Multi-line completion context (TC074)
- Performance/caching (covered separately)

## Prerequisites

- tq binary built in release mode with Sprint 11 fixes
- Valid Teradata connection configured in .env
- Live database with multiple databases (at least 2)
- Current database has multiple tables (at least 5)
- REPL mode functional

## Test Procedure

### Setup

```bash
# Start REPL with live database connection
./target/release/tq repl

# Verify connection successful
tq> /ping
# Should show "Connection OK"
```

### Execution Steps

**Step 1: Test basic FROM completion with no prefix**

Type this exactly (press Tab where shown):
```sql
tq> SELECT * FROM <TAB>
```

**Expected outcome:**
- Shows "Loading tables..." briefly if first time
- Displays list containing:
  - Database names (e.g., production, staging, dev)
  - Tables in current database (e.g., employees, orders, customers)
- **CRITICAL:** Does NOT show "(SQL keyword)" repeated 25 times
- **CRITICAL:** Shows actual database object names

**Step 2: Test FROM completion with partial prefix**

```sql
tq> SELECT * FROM emp<TAB>
```

**Expected outcome:**
- If "employees" table exists: auto-completes to "employees"
- If multiple matches (employees, employee_archive): shows list
- **CRITICAL:** Shows table names, not keywords
- Prefix matching works correctly

**Step 3: Test qualified name completion (database.table)**

```sql
tq> SELECT * FROM production.<TAB>
```

**Expected outcome:**
- Shows tables in "production" database
- Format: table names (not qualified yet - user types prefix)
- **CRITICAL:** Context detection recognizes "database." pattern

**Step 4: Test JOIN keyword completion**

```sql
tq> SELECT * FROM employees e JOIN <TAB>
```

**Expected outcome:**
- Same as FROM: shows databases + current DB tables
- **CRITICAL:** JOIN context detection works
- Not SQL keywords

**Step 5: Test UPDATE keyword completion**

```sql
tq> UPDATE <TAB>
```

**Expected outcome:**
- Shows table names from current database
- Context detection works for UPDATE
- Not SQL keywords

**Step 6: Test completion with spacing variations**

```sql
tq> SELECT * FROM<TAB>
tq> SELECT * FROM  <TAB>
tq> SELECT * FROM   <TAB>
```

**Expected outcome:**
- All three variations show same completion list
- Robust parsing handles spacing differences

### Verification

**Visual Inspection Checklist:**

- [ ] No "(SQL keyword)" strings anywhere in completion
- [ ] Actual database names visible (production, staging, etc.)
- [ ] Actual table names visible (employees, orders, etc.)
- [ ] Completion list makes semantic sense
- [ ] User can navigate to actual database objects

**Functional Validation:**

- [ ] Can select a completion and execute query successfully
- [ ] Completed table name is valid and queryable
- [ ] Completion speeds up query writing

### Cleanup

```bash
tq> /quit
```

## Expected Results

**Correct Completion Output (What we want):**

```
tq> SELECT * FROM <TAB>

Databases:
  production    staging    development

Tables in current database (production):
  customers    employees    orders    products    departments
```

OR (more compact format):

```
tq> SELECT * FROM <TAB>
production    staging    development    customers    employees    orders
```

**Key Characteristic:** Real database object names, not keywords.

## Anti-Pattern (What Should NOT Happen)

**INCORRECT Output from Bug:**

```
tq> SELECT * FROM <TAB>
(SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)
(SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)
(SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)
(SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)
(SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)  (SQL keyword)
```

This is exactly what the bug report screenshot shows - completely useless for the user.

## Pass/Fail Criteria

**PASS:**
- Tab after FROM shows databases and/or table names
- NO "(SQL keyword)" strings appear
- Completion list contains actual queryable objects
- Prefix matching filters correctly
- Context detection works for FROM, JOIN, UPDATE
- User can complete a real query successfully

**FAIL:**
- Shows "(SQL keyword)" repeated (bug not fixed)
- Shows only SQL keywords (SELECT, INSERT, etc.)
- No database/table names visible
- Completion list is empty when tables exist
- Context detection broken (shows keywords in table context)
- Cannot complete any real table name

## Notes

**Root Cause Context:**

This bug occurred because:
1. Context detection logic broke (likely in Sprint 10 batch mode changes)
2. Fallback to generic SQL keyword completion triggered incorrectly
3. Instead of showing "no completions available", showed keywords

**Why This Test Would Catch the Bug:**

- Tests actual completion output content (not just "completion triggered")
- Requires live database connection (mocks would pass incorrectly)
- Validates semantic meaning of completions (are they useful?)
- Checks specific failure mode (keywords vs. objects)

**Testing Philosophy:**

Previous tests may have verified:
- ✓ Completion mechanism works
- ✓ Tab key triggers completion
- ✓ Some output appears

But missed:
- ✗ Output is semantically correct
- ✗ Output is useful to user
- ✗ Output matches expected objects

This test fills that gap by validating the MEANING of completion results.
