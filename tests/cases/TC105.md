# TC105: `rust-toolchain.toml` — File Existence and CI Validation (Sprint 68)

**Sprint:** 68
**Feature:** Objective 4 — Pin CI toolchain via `rust-toolchain.toml` to eliminate rustc-drift hazard
**Component:** Project root `rust-toolchain.toml`, `.github/workflows/`, `src/lib.rs`
**Test Type:** Structural check (file read + grep, no DB) + local CI mirror execution
**Related Strategy:** `tests/strategy/sprint-68-strategy.md` — Objective 4
**Specification:** `docs/sprints/sprint-68-planning.md` → Objective 4 Acceptance Criteria

---

## Overview

Sprint 67 narrowly avoided a CI break when `#![deny(warnings)]` in `src/lib.rs` interacted with
a new clippy lint introduced in the latest stable Rust release. The root cause is that CI uses
`dtolnay/rust-toolchain@stable` without pinning, so a new stable release can introduce lints
that break CI without any developer action.

Mitigation: add `rust-toolchain.toml` to the project root. Rustup reads this file and applies the
specified toolchain for any `cargo` invocation inside the project directory. This makes toolchain
upgrades explicit rather than implicit.

Sprint 68 acceptance criteria require:
1. The file exists with a valid `[toolchain]` section.
2. `scripts/ci-check.sh` passes locally (local CI mirror).
3. CI passes on the sprint tag (remote, not locally verifiable).
4. The decision on `#![deny(warnings)]` is documented.

## TC105-file: Structural File Check

**Requirement:** AC-OBJ4-1 — file exists at project root with valid TOML structure.

**BLOCKED condition:** Never blocked.

### Verification Steps

```bash
# Step 1: File exists
ls -la rust-toolchain.toml

# Step 2: Contains [toolchain] section
grep "\[toolchain\]" rust-toolchain.toml

# Step 3: Contains channel key
grep "^channel" rust-toolchain.toml
```

**Pass criteria:**
- `ls` exits 0 (file present).
- `grep "[toolchain]"` returns a match.
- `grep "^channel"` returns a match with a value like `channel = "stable"` or a pinned version
  string like `channel = "1.95.0"`.

**Expected file content (minimal valid form):**
```toml
[toolchain]
channel = "stable"
```

Or with a pinned version:
```toml
[toolchain]
channel = "1.95.0"
```

Per the sprint planning doc, `channel = "stable"` is the recommended approach (not a hard version
string), but either form satisfies AC-OBJ4-1.

## TC105-local: Local CI Mirror

**Requirement:** AC-OBJ4-2 — `scripts/ci-check.sh` exits 0 after the toolchain file is added.
This is the local proxy for CI pass.

**BLOCKED condition:** Never blocked (no DB required for `ci-check.sh`).

### Verification Steps

```bash
# Run the local CI mirror
bash scripts/ci-check.sh
echo "Exit code: $?"
```

**Pass criteria:** Exit code is 0. Any non-zero exit is a FAIL for AC-OBJ4-2 (local proxy).

If `ci-check.sh` fails, inspect output for:
- Clippy lint errors — new lints from the pinned toolchain
- Test failures — regressions introduced by the sprint

**Note:** The toolchain pin does not change the behavior of `cargo test --lib`. The only possible
new failures are clippy lints that were already present but not triggered by the previous toolchain.

## TC105-ci: Remote CI Pass (Observation Only)

**Requirement:** AC-OBJ4-2 (remote) — GitHub Actions workflow must pass on the sprint commit or tag.

**BLOCKED condition:** Not a local test; requires a push to the remote repository.
This is NOT blocked — it is deferred to the sprint closure (Phase 5). The sprint is not APPROVED
until remote CI green is confirmed.

### Verification Steps

After the sprint commit is pushed and the `v1.50.0` tag is created:

```bash
# Check CI status (requires gh CLI)
gh run list --branch master --limit 5
gh run view <run-id> --log-failed
```

**Pass criteria:** All GitHub Actions jobs in the CI workflow pass (green checkmark on the commit).

### Failure Investigation

If CI fails after adding `rust-toolchain.toml`:
1. Check whether the pinned channel introduces new clippy lints not present locally.
2. Verify `rust-toolchain.toml` TOML syntax is valid (rustup is strict about keys).
3. Check if the `dtolnay/rust-toolchain@stable` action in `.github/workflows/` overrides the
   `rust-toolchain.toml` — some CI configurations explicitly set the toolchain via the action.
   If so, the workflow YAML may need to be updated to use the project's `rust-toolchain.toml`.

## TC105-doc: `#![deny(warnings)]` Decision Documentation

**Requirement:** AC-OBJ4-3 — the decision to keep or remove `#![deny(warnings)]` in `src/lib.rs`
must be documented.

**BLOCKED condition:** Never blocked.

### Verification Steps

**Step 1: Check current state of `src/lib.rs`**
```bash
grep -n "deny.warnings\|allow.warnings" src/lib.rs | head -5
```

**Step 2: For option A (keep `#![deny(warnings)]` with documentation)**

If the attribute is retained, a comment must explain the toolchain pin rationale:
```bash
grep -B2 -A2 "deny(warnings)" src/lib.rs
```
**Pass criterion:** A comment near `#![deny(warnings)]` references the toolchain pin (e.g.,
`// safe with rust-toolchain.toml pin`) or `docs/design/` contains a decision record.

**Step 3: For option B (remove `#![deny(warnings)]`, use CI `-D warnings`)**

If the attribute is removed, the CI workflow must use `-D warnings` as a compiler flag:
```bash
grep -r "D warnings\|deny.warnings" .github/workflows/
```
**Pass criterion:** At least one CI YAML file contains `-D warnings` in a `RUSTFLAGS` env var or
`cargo` invocation.

**Pass criterion (either option):** Either (A) `#![deny(warnings)]` is present in `src/lib.rs`
with a comment or design doc entry, OR (B) it is absent from `src/lib.rs` and `-D warnings`
appears in `.github/workflows/`. A third option — neither present anywhere — is a FAIL.
