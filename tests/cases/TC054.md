# Test Case TC054: Tab Completion - Cache Cleared After DROP TABLE DDL

## Purpose

Verify that the table metadata cache is invalidated after successful DROP TABLE statements, so dropped tables no longer appear in completion.

## Prerequisites

- tq REPL mode active
- Live Teradata database connection
- Permission to CREATE and DROP tables

## Test Procedure

### Step 1: Create test table

```sql
tq> CREATE TABLE test_drop_sprint8 (id INTEGER);
```

### Step 2: Verify table appears in completion

```sql
tq> SELECT * FROM test_d<TAB>
```

**Expected:**
- "test_drop_sprint8" appears in completion

### Step 3: Drop the table

```sql
tq> DROP TABLE test_drop_sprint8;
```

**Expected:**
- Table dropped successfully
- Cache invalidated automatically

### Step 4: Verify table no longer appears in completion

```sql
tq> SELECT * FROM test_d<TAB>
```

**Expected:**
- "test_drop_sprint8" does NOT appear
- Other tables starting with "test_d" may appear
- Empty completion if no matches (not an error)

### Step 5: Cleanup

```sql
tq> /quit
```

## Verification

- [ ] Table appears in completion after CREATE
- [ ] DROP TABLE executes successfully
- [ ] Dropped table does NOT appear in completion after DROP
- [ ] Cache refresh is automatic
- [ ] Other tables are unaffected

## Pass/Fail Criteria

**PASS:**
- Dropped table no longer appears in completion
- Cache is invalidated automatically on DROP
- Other tables remain in cache
- No manual refresh required

**FAIL:**
- Dropped table still appears in completion
- User must restart tq to update cache
- Cache is not invalidated on DROP
- All tables disappear from cache (over-invalidation)

## Notes

DDL statements triggering cache invalidation:
- DROP TABLE
- DROP VIEW
- RENAME TABLE
- ALTER TABLE (structural changes)

Invalidation should be scoped to affected database only.
