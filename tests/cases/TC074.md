# Test Case TC074: Tab Completion - Multi-Line Context Preservation (Regression Test)

## Purpose

Verify that Sprint 9 fix for multi-line completion context is still working after Sprint 10/11 changes. Tab completion must work correctly when the SQL statement spans multiple lines.

This is a REGRESSION TEST - ensuring we didn't break a previously working feature while fixing other issues.

## Scope

**Testing:**
- Multi-line SQL context detection
- Completion works on line 2, 3, 4+ of multi-line query
- Context preserved across line breaks
- FROM clause parsed correctly across lines
- Sprint 9 fix still intact

**Not Testing:**
- Single-line completion (other TCs)
- Complex nested queries
- Performance

## Prerequisites

- tq REPL connected to Teradata
- Test database with known tables (e.g., employees)
- Sprint 9 fix for multi-line completion was working
- Need to verify it still works after Sprint 10/11

## Test Procedure

### Setup

```bash
./target/release/tq repl

# Verify basic completion works first
tq> SELECT * FROM <TAB>
# Should show tables (if this fails, TC071 should catch it)
```

### Execution Steps

**Step 1: Test completion on second line of query**

```sql
tq> SELECT
    employee_id,
    first_name
  FROM <TAB>
```

**Expected outcome:**
- Tab completion triggers normally
- Shows database/table names
- Context parsing handles newlines
- FROM keyword detected even though on different line

**Step 2: Test column completion across lines**

```sql
tq> SELECT
    employee_id,
    <TAB>
  FROM employees
```

**Expected outcome:**
- Shows columns from employees table
- Context parser found FROM clause on next line
- Multi-line SELECT list handled

**Step 3: Test WHERE clause on separate line**

```sql
tq> SELECT *
  FROM employees
  WHERE <TAB>
```

**Expected outcome:**
- Shows columns from employees
- WHERE context detected
- FROM parsed from previous line

**Step 4: Test deeply nested multi-line query**

```sql
tq> SELECT
    e.employee_id,
    e.first_name,
    e.last_name
  FROM
    employees e
  WHERE
    e.department_id = 10
    AND e.<TAB>
```

**Expected outcome:**
- Context preserved through 6+ lines
- Shows columns from employees (with alias 'e')
- Complex multi-line parsing works

**Step 5: Test completion after pressing Enter multiple times**

```sql
tq> SELECT * FROM
<Enter>
<Enter>
<TAB>
```

**Expected outcome:**
- Context still valid (FROM keyword found)
- Shows table completion
- Empty lines don't break context

**Step 6: Test mixed single/multi-line queries**

```sql
# Single line - should work
tq> SELECT * FROM <TAB>

# Multi-line - should also work
tq> SELECT *
  FROM <TAB>

# Back to single line - should still work
tq> SELECT * FROM <TAB>
```

**Expected outcome:**
- Both modes work correctly
- No state corruption between queries
- Context detection robust

### Verification

**Regression Checklist:**

- [ ] Multi-line completion works (Sprint 9 fix intact)
- [ ] Single-line completion works (TC071)
- [ ] No state corruption between query types
- [ ] Context parser handles newlines correctly

**Functional Validation:**

Complete a multi-line query successfully:
```sql
tq> SELECT
    employee_id,
    first_name
  FROM employees
  WHERE department_id = 10;

# Should execute and return results
```

### Cleanup

```bash
tq> /quit
```

    e.department_id = 10
    AND e.<TAB>

  e.employee_id    e.first_name    e.last_name    e.email

## Anti-Pattern (What Should NOT Happen)

**INCORRECT Behavior (Regression):**

```
tq> SELECT
    employee_id
  FROM <TAB>

(No completion - context lost)
```

OR

```
tq> SELECT
    employee_id
  FROM <TAB>

SELECT    INSERT    UPDATE    DELETE    (SQL keywords - wrong context)
```

This would indicate multi-line context parsing is broken again.

## Pass/Fail Criteria

**PASS:**
- Completion works on line 2+ of multi-line query
- FROM clause parsed from any line
- Column completion finds table across lines
- WHERE completion works after multi-line SELECT/FROM
- Context preserved through empty lines
- Sprint 9 fix still working
- No regression introduced

**FAIL:**
- Completion breaks on multi-line queries
- Context lost after newline
- Shows keywords when should show tables/columns
- FROM keyword not detected on different line
- Regression from Sprint 9 behavior
- State corruption between queries

## Notes

**Sprint 9 Fix Context:**

Sprint 9 specifically fixed multi-line completion context:
- Problem: Context lost after Enter key
- Fix: Buffer entire multi-line query for parsing
- Test: Verified completion worked across lines

**Why This Regression Test Matters:**

Sprint 10 made batch mode changes that could affect:
- Query buffering logic
- Context parsing
- State management

Sprint 11 fixes completion bug that might:
- Change parser implementation
- Affect multi-line handling
- Break Sprint 9 fix inadvertently

**What to Watch:**

If this test fails:
1. Check if buffer cleared prematurely
2. Verify parser sees entire query, not just last line
3. Look for state reset on newline
4. Compare to Sprint 9 working implementation

**Implementation Insight:**

Completion context parser must:
- Receive entire buffered query (all lines)
- Parse SQL across newlines
- Maintain state between keystrokes
- Not be fooled by Enter key
