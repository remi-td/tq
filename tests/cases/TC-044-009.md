# TC-044-009: display_profiles() Helper Produces Correct Output

**Sprint:** 44
**Feature:** Technical Debt Cleanup (AC-21)
**Acceptance Criteria:** AC-21
**Type:** Unit Test
**Requires DB:** No
**Requires Binary:** No

---

## Objective

Verify that the extracted `display_profiles()` helper function produces the correct formatted output for profile listing. The output must be identical to what `handle_list` previously produced inline, ensuring that extracting the helper does not change user-visible behavior.

AC-21: "Shared `display_profiles()` helper extracted from `handle_list`/`handle_profiles`"

## Preconditions

- `display_profiles()` function exists in `src/commands/profile.rs` or `src/main.rs`
- The function is called by both `handle_list` and `handle_profiles` (the existing `tq profiles` command handler)

## Test Scenarios

### Scenario 1: Empty profile config produces "no profiles" message

**Setup:** `Config` with empty `profiles` map

**Action:** Call `display_profiles(&config)` and capture stdout

**Expected:** Output contains "No profiles defined" (or similar)

**Assert:**
```rust
let config = Config::default();
// Capture stdout during the call
// OR if display_profiles returns a String, assert the string content
let output = capture_stdout(|| display_profiles(&config));
assert!(output.contains("No profiles defined") || output.contains("no profiles"),
    "Empty profiles should produce 'no profiles' message, got:\n{}", output);
```

### Scenario 2: Single profile displayed with correct fields

**Setup:** `Config` with one profile named `"dev"`:
- host: `"dev.example.com"`
- database: `"devdb"`
- user: `"alice"`
- logmech: None (default TD2)

**Action:** Call `display_profiles(&config)`

**Expected output contains:**
```
dev
  Host:     dev.example.com
  Database: devdb
  User:     alice
```

**Assert:** Output contains each expected line

**Note:** `logmech` with value `TD2` (or None) should NOT be displayed (non-default logmech only shown)

### Scenario 3: Profile with non-default logmech shows logmech field

**Setup:** Config with profile `"prod"`:
- host: `"prod.example.com"`
- logmech: `Some("LDAP")`

**Expected:** Output contains `"Logmech: LDAP"` (or similar)

**Assert:**
```rust
assert!(output.contains("LDAP"), "Non-TD2 logmech should be shown in output");
```

### Scenario 4: Multiple profiles displayed in sorted order

**Setup:** Config with profiles `"prod"`, `"dev"`, `"staging"` (inserted out of alphabetical order)

**Expected:** Output shows `dev`, then `prod`, then `staging` (alphabetical)

**Assert:**
```rust
let dev_pos = output.find("dev").unwrap();
let prod_pos = output.find("prod").unwrap();
let staging_pos = output.find("staging").unwrap();
assert!(dev_pos < prod_pos, "dev should appear before prod (alphabetical)");
assert!(prod_pos < staging_pos, "prod should appear before staging");
```

### Scenario 5: Output from `handle_list` equals output from `display_profiles`

**Setup:** Config with one profile

**Action:**
1. Capture stdout of `handle_list(&config)` call
2. Capture stdout of `display_profiles(&config)` call

**Expected:** Both outputs are identical (same text, same format)

**Assert:** `output_from_handle_list == output_from_display_profiles`

This ensures the extraction did not accidentally change the output format.

## Implementation Notes

If `display_profiles()` writes directly to stdout (using `println!`), capturing output in tests requires a helper. One approach is to have the function accept a `writer: &mut dyn Write` parameter:

```rust
pub fn display_profiles(config: &Config, writer: &mut dyn std::io::Write) -> Result<()> {
    if config.profiles.is_empty() {
        writeln!(writer, "No profiles defined.\n")?;
        writeln!(writer, "To create a profile:\n  tq profile add <name> ...")?;
        return Ok(());
    }
    // ... rest of output
}
```

This enables tests to pass a `Vec<u8>` as the writer and inspect the output as a string.

If the implementation writes to stdout directly, tests can use `std::io::BufWriter` redirection or observe side effects through the test harness.

## Test Code Sketch

```rust
#[test]
fn test_display_profiles_empty_config() {
    let config = Config::default();
    let mut output = Vec::new();
    display_profiles(&config, &mut output).unwrap();
    let text = String::from_utf8(output).unwrap();
    assert!(text.to_lowercase().contains("no profile"),
        "Empty config should indicate no profiles, got:\n{}", text);
}

#[test]
fn test_display_profiles_single_profile_all_fields() {
    let mut config = Config::default();
    config.profiles.insert("dev".to_string(), crate::config::ConnectionSettings {
        host: Some("dev.example.com".to_string()),
        database: Some("devdb".to_string()),
        user: Some("alice".to_string()),
        ..Default::default()
    });
    let mut output = Vec::new();
    display_profiles(&config, &mut output).unwrap();
    let text = String::from_utf8(output).unwrap();
    assert!(text.contains("dev.example.com"), "Host should be shown");
    assert!(text.contains("devdb"), "Database should be shown");
    assert!(text.contains("alice"), "User should be shown");
}

#[test]
fn test_display_profiles_sorted_alphabetically() {
    let mut config = Config::default();
    config.profiles.insert("prod".to_string(), crate::config::ConnectionSettings {
        host: Some("prod.host".to_string()), ..Default::default()
    });
    config.profiles.insert("dev".to_string(), crate::config::ConnectionSettings {
        host: Some("dev.host".to_string()), ..Default::default()
    });
    let mut output = Vec::new();
    display_profiles(&config, &mut output).unwrap();
    let text = String::from_utf8(output).unwrap();
    let dev_pos = text.find("dev.host").unwrap();
    let prod_pos = text.find("prod.host").unwrap();
    assert!(dev_pos < prod_pos, "dev should appear before prod in sorted output");
}
```

## Pass Criteria

- Empty config produces "no profiles" message
- Single profile shows host, database, user (when set)
- Non-TD2 logmech shown; default TD2 not shown
- Multiple profiles appear in alphabetical order
- Output of `handle_list` and `display_profiles` is identical (extraction did not change behavior)
