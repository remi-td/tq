# TC-046-002: Bug #35 — extract_table_name Word Boundary Matching

## Metadata

## Purpose

Verify that after the Bug #35 fix, `extract_table_name()` uses word-boundary matching when searching for SQL keywords (FROM, INTO, UPDATE, TABLE). The current bug: `sql_upper.find("TABLE")` matches "TABLE" inside "TABLES", so `SELECT * FROM TABLES` extracts only "S" (the suffix after "TABLE") as the table name.

The fix must ensure keyword matches only when "TABLE" (or any keyword) is followed by whitespace or end of string — i.e., it is a complete word, not a substring.

## Acceptance Criteria Coverage

- **AC-8**: Unit tests for `extract_table_name()` word boundary matching
- **AC-6**: `extract_table_name` correctly extracts table from `SELECT * FROM "DBC"."TABLES" SAMPLE 10`

## Prerequisites

- `src/db/client.rs` has `extract_table_name()` fixed to use word-boundary matching
- `cargo test --lib` compiles successfully

## Test Procedure

### Understanding the Bug

Current code (buggy):
```rust
if let Some(pos) = sql_upper.find("TABLE") {
    // "TABLES" contains "TABLE" at pos 0
    // sql[pos + "TABLE".len()..] = "S ..."
    // extract_table_name returns "S" -- wrong!
}
```

Fixed approach: keyword must be matched as a complete word. One correct implementation checks that the character following the keyword position is whitespace (or end of string) and the character before is also a word boundary (start of string or whitespace or quote).

### Test Implementation (in `src/db/client.rs` `#[cfg(test)]` module)

Add the following test functions to the existing `tests` module:

```rust
// TC-046-002-A: Basic FROM extraction — original regression test preserved
#[test]
fn test_extract_table_name_from_basic() {
    assert_eq!(
        extract_table_name("SELECT * FROM employees WHERE id = 1"),
        Some("employees".to_string())
    );
}

// TC-046-002-B: "TABLES" — must NOT extract "S" from "TABLE" substring
// This is the core bug scenario
#[test]
fn test_extract_table_name_tables_not_s() {
    let result = extract_table_name("SELECT * FROM tables");
    // Must be Some("tables"), not Some("s")
    assert_eq!(result, Some("tables".to_string()));
}

// TC-046-002-C: Quoted qualified name "DBC"."TABLES" — AC-6 scenario
// After the identifier quote fix, the SQL becomes:
//   SELECT * FROM "DBC"."TABLES" SAMPLE 10
// extract_table_name must find something meaningful (not "S")
#[test]
fn test_extract_table_name_quoted_qualified_tables() {
    let sql = r#"SELECT * FROM "DBC"."TABLES" SAMPLE 10"#;
    let result = extract_table_name(sql);
    // Must not be Some("s") or None
    // The exact extracted value depends on implementation (may include quotes)
    // but must NOT be the substring bug result "s"
    assert!(result.is_some());
    let name = result.unwrap();
    assert_ne!(name.to_lowercase(), "s", "Must not extract 's' from 'TABLES' substring");
}

// TC-046-002-D: INTO keyword with "tablesv" — word boundary after INTO
#[test]
fn test_extract_table_name_into_word_boundary() {
    assert_eq!(
        extract_table_name("INSERT INTO tablesv VALUES (1, 2)"),
        Some("tablesv".to_string())
    );
}

// TC-046-002-E: UPDATE keyword — word boundary
#[test]
fn test_extract_table_name_update_word_boundary() {
    assert_eq!(
        extract_table_name("UPDATE tablesv SET col1 = 1 WHERE id = 5"),
        Some("tablesv".to_string())
    );
}

// TC-046-002-F: TABLE keyword (as used in CREATE TABLE context)
// "FROM TABLESPACE" must not extract "SPACE" — but TABLE is not FROM,
// this tests that the FROM keyword itself is not confused with TABLE
#[test]
fn test_extract_table_name_from_wins_over_table_substring() {
    // "SELECT col FROM tablesummary WHERE TABLE_ID = 1"
    // "FROM" keyword matches "tablesummary" — not confused by "TABLE_ID" later
    let result = extract_table_name("SELECT col FROM tablesummary WHERE TABLE_ID = 1");
    assert_eq!(result, Some("tablesummary".to_string()));
}

// TC-046-002-G: No SQL keyword present — returns None
#[test]
fn test_extract_table_name_no_keyword_returns_none() {
    assert_eq!(extract_table_name("SHOW TABLES"), None);
}

// TC-046-002-H: Lowercase keywords in SQL (the function uppercases before search)
#[test]
fn test_extract_table_name_lowercase_keyword() {
    assert_eq!(
        extract_table_name("select * from dbc.tables sample 10"),
        Some("dbc.tables".to_string())
    );
}
```

## Expected Results

All 8 unit tests pass:

- `test_extract_table_name_tables_not_s` — PASS: `Some("tables")` returned (not `Some("s")`)
- `test_extract_table_name_quoted_qualified_tables` — PASS: result is `Some(...)` and not `"s"`
- `test_extract_table_name_into_word_boundary` — PASS: `Some("tablesv")` returned
- `test_extract_table_name_update_word_boundary` — PASS: `Some("tablesv")` returned

- `test_extract_table_name_no_keyword_returns_none` — PASS: `None` returned

## Pass/Fail Criteria

**PASS if:**
- All 8 tests compile and pass
- "TABLES" does not produce "s" as the extracted table name
- FROM/INTO/UPDATE keyword matching is not fooled by substring matches

**FAIL if:**
- `test_extract_table_name_tables_not_s` returns `Some("s")` — indicates the bug is not fixed
- Any keyword extraction is broken (regression)
- `test_extract_table_name_quoted_qualified_tables` returns `Some("s")` — indicates bug persists with quoted identifiers

## Notes

- `extract_table_name` is a private function in `src/db/client.rs`. Tests must be in the `#[cfg(test)]` module inside the same file.
- The test for TC-046-002-C (`quoted_qualified_tables`) uses a lenient assertion (not `"s"`) because the exact extracted string for `"DBC"."TABLES"` depends on how the implementation handles quoted identifiers in the FROM clause. The critical invariant is that the substring bug does not produce `"s"`.
- If the implementation uses regex with `\bTABLE\b`, verify the regex is correct for Rust's `regex` crate (not std).
- If the implementation uses a manual character-by-character boundary check, verify both the character before and after the keyword.
