# Test Case TC045: Table Formatting - Wide Table with 16+ Columns

## Purpose

Verify that tables with many columns (16+) display correctly without excessive padding. This test reproduces the original bug where `DBC.Databases` (16 columns) was completely unreadable.

## Scope

**Testing:**
- Wide table layout (16+ columns)
- Terminal width constraint handling
- Column width calculation with many columns
- Horizontal scrolling or wrapping behavior

**Not Testing:**
- JSON/CSV formats
- Paging (covered in TC057-TC063)
- Column-specific alignment rules

## Prerequisites

- tq REPL mode active
- Live Teradata database connection
- Terminal width at least 80 columns (standard)
- DBC.DatabasesV access (or equivalent 16+ column table)

## Test Procedure

### Setup

```bash
# Start tq in REPL mode
./target/release/tq

# Note your terminal width
tput cols
```

### Execution Steps

**Step 1: Query DBC.Databases with all columns (reproduces original bug)**

```sql
tq> SELECT TOP 3 * FROM DBC.DatabasesV;
```

**Expected outcome:**
- Table displays with all 16 columns
- Table either:
  - Fits in terminal width with reasonable column sizing, OR
  - Clearly indicates horizontal scrolling is needed, OR
  - Wraps intelligently
- NO excessive padding (columns should not be 60+ characters wide for 3-character data)

**Step 2: Verify column width sanity**

Observe the output and measure:
- Width of "DatabaseName" column
- Actual max data width in that column (e.g., "TD_SYSXML" = 10 chars)
- Padding should be reasonable: max_data_length + 1-3 chars for padding

**Formula Check:**
```
Acceptable column width = max(header_length, max_data_length) + 2 padding
```

For "DatabaseName" with data "TD_SYSXML":
- Header length: 12
- Max data length: ~10
- Acceptable width: 12-14 characters
- NOT ACCEPTABLE: 60+ characters

**Step 3: Verify terminal width awareness**

```sql
tq> SELECT DatabaseName, CreatorName, OwnerName, AccountName, ProtectionType,
    JournalFlag, PermSpace, SpoolSpace, TempSpace, CommentString,
    CreateTimeStamp, LastAlterName, LastAlterTimeStamp, DBKind,
    AccessCount, LastAccessTimeStamp
    FROM DBC.DatabasesV
    WHERE DatabaseName = DATABASE;
```

Check if table:
- Detects terminal width
- Adjusts column widths to fit terminal
- Maintains readability

**Step 4: Test with narrow terminal**

```bash
# Resize terminal to 100 columns (if possible)
# Or note current width
```

Re-run Step 1 query and observe behavior:
- Does table adapt to terminal width?
- Are columns still readable?
- Is there graceful degradation (e.g., truncation, wrapping)?

### Verification

**Critical Checks:**

1. **No Excessive Padding:**
   - [ ] NO columns are 60+ characters wide when data is <10 characters
   - [ ] Column widths are proportional to data, not arbitrary

2. **Terminal Width Awareness:**
   - [ ] Table total width ≤ terminal width, OR
   - [ ] Clear indication that horizontal scrolling is needed

3. **Readability:**
   - [ ] Headers and data still align (not broken by excessive width)
   - [ ] Can identify which value belongs to which column
   - [ ] Separators are visible and consistent

4. **Performance:**
   - [ ] Table renders in <2 seconds (not hung on formatting)

**Measurements:**

For each column, record:
- Header text length
- Longest data value length
- Actual rendered column width

Compare: Rendered width should be close to `max(header, data) + padding`, NOT `max_column_width * column_count`.

## Pass/Fail Criteria

**PASS:**
- Column widths are reasonable: ~max(header_len, data_len) + 2-5 padding
- NO columns exceed 40 characters unless data requires it
- Table total width ≤ terminal width + 20% (allows minor overflow)
- Headers and data remain aligned
- Table renders in <2 seconds

**FAIL:**
- ANY column has excessive padding (>3x data length)
- Table total width >> terminal width (e.g., 960 chars on 120 char terminal)
- Headers and data misalign
- Table is unreadable due to width issues
- Rendering hangs or takes >5 seconds

## Notes

**Root Cause Context:**

The original bug was in `src/format/table.rs`:
```rust
table.set_width(max_column_width * result.columns.len() as u16);
```

This multiplied 80 (max_column_width) * 16 (columns) = 1280 total width, making the table completely unreadable.

**Expected Fix:**

The fix should:
1. Remove the erroneous `set_width` calculation
2. Use `ContentArrangement::Dynamic` or `DynamicFullWidth`
3. Detect terminal width via `crossterm::terminal::size()`
4. Let comfy-table calculate appropriate widths per column
5. Possibly set per-column constraints via `Column::set_constraint()`

**This is the PRIMARY bug reproduction test.** If TC045 passes, the core bug is fixed.

**Terminal Width Detection:**

To verify terminal width detection works:
```bash
# Get terminal size
tput cols
tput lines

# In Rust (what tq should use):
# crossterm::terminal::size() returns Result<(cols, rows)>
```

The fix must respect the actual terminal width, not assume arbitrary values.
