## Purpose

Verify that tab completion works correctly after the SELECT keyword, showing available column names from the table referenced in the FROM clause with type hints.

## Scope

This test validates:
- Tab completion after SELECT keyword
- Table context detection from FROM clause
- Column list loaded from database metadata
- Type hints displayed with column names
- Performance meets <300ms requirement
- Column metadata caching

## Prerequisites

- tq binary built in release mode
- Valid Teradata connection credentials configured in .env
- Test database with tables containing multiple columns
- Access to DBC.ColumnsV system catalog
- REPL mode functional
- Table completion working (TC026 passed)

## Test Procedure

### Step 1: Start REPL
```bash
tq repl
```

### Step 2: Type SELECT with table in FROM clause, then Tab
```sql
tq> SELECT * FROM employees WHERE <TAB>
```

**Expected behavior:**
- Detects "employees" as table context
- Loads columns for employees table
- Displays column names with type hints

### Step 3: Test SELECT clause completion
```sql
tq> SELECT <TAB> FROM employees
```

**Note:** This may show "(Cannot determine table context)" if parser reads left-to-right.
This is acceptable v1 behavior - user should type FROM clause first.

### Step 4: Test prefix matching in SELECT
```sql
tq> SELECT * FROM employees WHERE emp<TAB>
```

**Expected behavior:**
- Filters to columns starting with "emp"
- Auto-completes if single match
- Shows list if multiple matches

### Step 5: Test multiple column selection
```sql
tq> SELECT employee_id, first<TAB>
    FROM employees
```

**Expected behavior:**
- Completes "first" to "first_name" if unique
- Shows matching columns

### Step 6: Verify caching on second completion
```sql
tq> SELECT * FROM employees WHERE <TAB>
# Then again:
tq> SELECT * FROM employees ORDER BY <TAB>
```

**Expected behavior:**
- First time: "Loading columns for 'employees'..." (< 300ms)
- Second time: Instant (< 50ms)

### Step 7: Test type hints display
```sql
tq> SELECT * FROM employees WHERE <TAB>
```

**Expected behavior:**
- Displays format: column_name (TYPE)
- Examples: employee_id (INTEGER), first_name (VARCHAR), hire_date (DATE)

### Step 8: Test case-insensitive matching
```sql
tq> SELECT * FROM employees WHERE EMP<TAB>
tq> SELECT * FROM employees WHERE Emp<TAB>
tq> SELECT * FROM employees WHERE emp<TAB>
```

**Expected behavior:**
- All produce same matches

## Pass/Fail Criteria

**PASS if:**
- Column completion works after WHERE/ORDER BY
- Table context detected from FROM clause
- Column list loads from metadata
- Type hints displayed correctly
- Performance < 300ms first time, < 50ms cached
- Prefix matching filters correctly
- Caching works for subsequent completions
- Case-insensitive matching
- No crashes or errors

**FAIL if:**
- Completion doesn't trigger
- Wrong columns displayed
- No type hints shown
- Performance exceeds 300ms consistently
- Caching doesn't work
- Case-sensitive only
- Crashes or errors

## Notes

- Column metadata queried from DBC.ColumnsV
- Type hints help users understand column data types
- Context detection may have limitations (subqueries, CTEs) - acceptable for v1
- If FROM clause not yet typed, can't detect context - should show helpful message
- Performance critical since columns queried per table
